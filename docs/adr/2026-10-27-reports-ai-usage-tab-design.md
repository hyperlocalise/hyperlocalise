# Reports: the AI usage tab

**Status:** Accepted

Builds on [Reports rework](./2026-10-23-reports-rework-design.md), whose rule for placing each AI call in a task and project (`ai-attribution.ts`) it reuses. No migration and no change to billing's code.

## Context

AI is part of every paid plan, so admins and localization managers need to see where it goes. The Activity tab had a small AI usage section, grouped by one of area or model, with tokens only. It added calls on the workspace's own provider key to calls through Hyperlocalise, and it filed some calls under the wrong area: GitHub commit and pull request reviews under "Other", text read from images as images made.

## Decision

- **Its own tab**, after Time: Activity, Word counts, Time, AI usage, Costs, Cost estimate, Budgets. For `billing:read`, like the rest of Reports. Activity no longer shows AI.
- **Only what billing already records** (`usage_events`). Recording more for each call (who started it and which API key, whose columns `actor_user_id` and `api_key_id` exist unfilled; the split of cached from reasoning tokens; language) would touch about 30 callers of billing's recorders and is left for its own change.
- **Details.** Each call can be grouped and narrowed by area, feature (billing's `source`, with a plain name for each known one), model, provider (the part of the model id before `/`), channel, key (Hyperlocalise AI, the workspace's own key, or not recorded), project, task and automation (`a.id`, newly exposed by `attributedUsage`). The table groups by one detail and optionally a second, 50 first-level groups a page, each with its 10 largest groups by the second detail and the rest as one "Other" row, whose credit is summed in the database so rounding each row does not add up (a CSV has every row); "largest" is by the chart's measure (tokens, runs or AI credit), so the costliest groups never hide in "Other" on the credit view; the chart stacks the period's five largest groups, per day (per week above 45 days), and the rest as "Other"; the headline numbers compare with the period before.
- **Every figure from billing's token rows.** Billing reserves a row for each image or video and writes a token row under it once it is made; a failed one leaves only the reservation. So each token row is one finished billed use of AI, shown as an "AI run": a task, an automation run, a chat turn or a single request, not one model request (a task makes many); the API keeps the field name `calls`. A token row under an image or video counts as that image or video, never as a run, and carries its model, key and charge. Its tokens count as they are: the image model's own when it reports them, else one per image (a video's are its seconds), which is little next to real tokens and needs no rule to tell the two apart. A video's model, and an image's when the model reports no usage, is billing's pricing name (`custom/…`), so Provider shows "custom" for them. Reservations are not read.
- **Tokens are every token billing counts.** Input and output leave out cached input and reasoning, which billing counts in the row's `quantity` and charges; the tab shows them as "cache and reasoning" (`quantity` less input and output) and the Tokens figure is the total. Images and videos from before AI credit pricing (about September 2026) had no token row and are not counted.
- **Billing's charge, never an estimate**, shown as "AI credit used" (plan credit; overage was removed from pricing, so it is not invoiced). Each group shows `amount_usd` summed over rows through our gateway, as Costs does. Rows on the workspace's own key show "Own key" and count apart. A row with no charge recorded (not received, failed, or from before billing recorded the key) counts as "not recorded", never as $0, on the card and in the table, and the card makes no comparison with a period where more than 5% of the runs on our AI have no credit recorded (a few are always on their way; a period mostly from before billing recorded charges is no base); a charge below a cent shows as "Under $0.01". The chart's charge and the CSV are plain numbers, with the not-recorded count beside them in the CSV. This revises the rework's "tokens only, never money" for AI usage, within its own condition that money comes only from billing.
- **One set of rules for where a call came from.** The area and channel rules are data (`ORIGIN_RULES`, `CHANNEL_RULES` in `ai-usage-origins.ts`); the page's functions and the SQL that groups and filters by them are built from the same rules, and a test checks every named source gives the same answer in both.
- **Corrected placements** (from reading every place that writes a source): GitHub commit and pull request reviews are Review and QA, channel GitHub; answering a person's mention in a GitHub pull request is Assistants and chat, channel GitHub; a connected TMS's "leave a comment" run is Review and QA; reading the text in an image is a call with tokens, not an image made. Three source names no code writes were dropped.
- **API and MCP match the page:** `GET /reports/ai-usage` and `GET /reports?report=ai` take `groupBy`, `thenBy`, `rankBy`, the filters and `page`, with `format=csv` for every group; the MCP `get_report` tool takes `report: "ai"` with the same fields.
- **An automation's tool steps belong to it.** Only an automation's main run records `automation_id`; its tool steps (GitHub, GitLab, web search, Semrush, Ahrefs, Crowdin, Zernio) record the run in their key, `workspace-<tool>:<run id>:…`. `attributedUsage` looks the run up in `workspace_automation_runs`, so their AI counts in the automation and, through it, in its project; Costs and Budgets count it there too. The Crowdin step's one-off review suggestions carry no run and stay outside any project.
- **The parent lookup skips token rows.** A token row is only ever a child (`<parent>:ai_tokens`), so `attributedUsage` no longer looks for parents among them; results are the same, and the large benchmark workspace's year read went from about 1.1 s to 0.75 s.
- **Narrowing** works where a filter stands for the row: not for a group of calls without the detail ("No task", "Outside any project"), "Other", or rows under them; a row whose filter is already set (the chosen project, task or model) is text, and the rows under it narrow within it. A task picked from a row is named in the Task field even when Reports never counted its strings (the picker's lookup by id does not need a Reports analysis; its search still does). A project row keeps the chosen task; changing project in the filter bar drops an automation filter.

## Consequences

- On the large benchmark workspace (240,000 AI calls a year), the tab reads in about 0.09 s for 28 days and 0.19 s for 90 days, but about 0.75 s for a year grouped by task (the same for a download of every group), against the 0.2 s mark of the other tabs. The three reads (totals with the period before, table, chart) run side by side; reading the billing rows once for all three was slower (1.3 s), because it lost that and held two years of rows. This was judged fast enough. The chart's query is most of a year's time (it sorts every row twice); adding up by day and group first roughly halves it, and a daily AI summary table would meet the mark at the cost of a migration and a way to see billing's later changes to a row (its charge arrives after the call).
- The table pages with window functions rather than a join, so a CSV of every group stays linear, and a page past the end still says how many groups there are.
- The channel of `chat_translate_string`, and of translation tasks started from Slack, an automation or an integration, shows App: the source does not say where the call started.
- Where a call is placed rests on names other code chooses: prefixes of `source` and, for automation tool steps, the run id in the operation key (a test reads the tool files and checks each key puts the run second). A renamed key or source moves AI on Costs and Budgets too. The way to retire the key parsing is for the tool callers to add `automation_id` to the dimensions they already pass; the parsing would still be needed for older rows.
- A task's or automation's project is its project now, so moving one to another project moves its past AI with it, as on Costs and Budgets.
- AI credit here is by UTC day; the billing page shows the billing cycle. A "this billing period" range is not offered yet.
- The comparison with the period before follows Reports' start, like the other tabs, though billing's rows may go back further.
- Changing a source name in billing's callers, or adding one, needs its area and channel set in `ai-usage-origins.ts` and a plain name on the page; an unknown source shows under "Other" with its raw name.

## Alternatives considered

- **Links only, tokens only:** keep the tab without money and link to Costs and the billing page. Chosen against by the user: no tab showed AI money by area, model, task or automation.
- **Grouping in the app after reading every combination:** simpler SQL, but grouping by task over a year would send hundreds of thousands of rows to the app, and paging and filtering by area or channel would have to happen there too.
- **One statement for all three reads:** slower, as above.
