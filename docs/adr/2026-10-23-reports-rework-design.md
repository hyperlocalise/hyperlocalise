# Reports rework: daily summary, money and the new pages

**Status:** Accepted

Ships as one pull request (`feat/web-reports-task-report`), built in three parts: the daily summary, the read layer and API, and the Reports page with a task's Report tab. It builds on [Reports capture rework](./2026-10-20-reports-capture-rework-design.md), which records the work this reads. The whole rework is one migration, `0161_reporting_rework`. A follow-up (`fix/web-reports-follow-ups`, migration `0162_reporting_follow_ups`) changed how work is priced and attributed, how a project's rows count, and how a task's analysis reports its state; this record describes the result.

## Context

Reports (behind the `workspace-reports` flag, no customer users yet) records words, match bands, completions, logged time and costs. Users asked for word counts per project, language and task by match band, time per task, budgets, and analytics: weekly volume, time per step and AI usage.

- The page was one table over the raw records. Finished-word totals join `reporting_activity` to `reporting_analyses`; for a large workspace (5.4 million analysis rows a year) each section took 2 to 7 seconds.
- Reports priced AI itself with `tokenlens`, which has no prices for the default managed models, while billing already records what each call is charged ([AI spend tracking](./2026-09-01-ai-spend-tracking-design.md)).
- Rates were per word only, and a task's own rate was one rate line used for every language of the task.
- Rollout was one date for every workspace (`reporting_rollout`).

## Decision

### Daily summary

- `reporting_daily_by_task` keeps, per workspace, project, task, source and target language, step, match band, where the finished text came from (`source`: memory, ai, person, import, unknown, or "" on a row that only holds arrivals), payable flag and UTC day: source, arrived, arrived and done, abandoned (arrived, not done, and held by no open task: its task failed, was cancelled or deleted, or was marked done with the string left over, so no more work will come from it), finished, finished by a person, and finished unchanged (a person kept the text they were given), each in words, strings, characters and characters with spaces, plus strings whose units could not be counted. Neither daily table has a unique key, so a deleted project's rows go with it and nothing collides.
- `reporting_daily_by_project` is the same without task, source language and payable, and counts each string once per text, language and step however many tasks hold it, as every other platform counts a project: on its earliest current analysis, done if any task finished it, abandoned if no open task holds it; its source counts each text once across tasks and languages too. So a project's rows are not the sum of its tasks' rows where tasks overlap; the finished rows are. The refresh reads every current analysis of the strings arriving in the refreshed days to decide this, and a write that changes which analysis of a string is current, or finishes one, marks the days of that string's other current analyses in any task of the project, so the project's rows follow.
- `reporting_current_by_project` keeps each project's current strings by language, step and match band, each string once by its newest current analysis however many tasks hold it, with that analysis's own source language; rewritten from the raw analyses by the scheduled run only, once per project per run (a task's own refresh leaves it alone), so a whole project can be estimated without reading its days and without counting a string per task.
- "Arrived" counts the current version of each string; "finished" counts every finished record. Each completion records where its text came from (`reporting_activity.source`) and, for a person's save, whether they kept the text they were given (`unchanged`, from the editor's own version history: the latest version not written by a person against the text saved). A person's save keeps the given text's source when they kept it, else it is their own.
- A task for people (a proofread task, a visual workflow's translate, post-edit or proofread task) runs no agent, so its strings are recorded as arrived when it is created, payable, in a workflow started off the request (`taskAnalysisWorkflow`): one step per language, retried by the runtime, so a retry keeps the languages already recorded and each language has a step's whole time; a language whose memory cannot be read or scored after every retry is recorded without match bands and the task's quote says it is not exact (only that failure: a database error or a step out of time fails the analysis, since strings without bands are priced as new work and that stays). A last step then refreshes the task's days in the summary at once rather than at the next scheduled run, waiting a few seconds for a scheduled run that holds the project, skipping days it did meanwhile, and leaving the days' marks and the project's current rows to that run. The strings go under the step the task is for: translation for a translate task, review for a post-edit or proofread task (their kind is proofread). String tasks have no file and are not analysed.
- `reporting_task_analyses` holds the state of each step's analysis (pending, done or failed, with whether the quote is not exact, the task's strings and the last error), set pending when the task is created, written by the workflow, deleted with the task; a pending state not updated for an hour reads as failed. The task's Report tab reads it (`GET /tasks/:jobId/analysis`; the counts and failure details only for the roles that see the task's words) every few seconds while pending, says its strings are being counted or could not be, and reads the report again once they are, rather than guessing from the task's age; strings counted but not yet in the summary make it read the report again in a while.
- A save in the content editor belongs to the newest task for people covering the string's file, language and step that was open when the save was made (still open, or ended after it, since saves reach Reports some minutes later); jobs an agent ran never count. An edit (a translation-step save) made while a proofread task covers the string, with no translate task for people open, is that task's review work, at its review rate: reviewers edit inside proofread and post-edit tasks. Otherwise the save belongs to the task that produced the translation. Whether a person kept the text they were given is judged from the editor's own history at the time of their save (the version the save names, else the latest by then), not from the translation when the capture runs, which a job may have overwritten since.
- **Every write to `reporting_analyses` or `reporting_activity` marks its workspace, project and UTC day in `reporting_summary_queue` in the same transaction** (`markSummaryDays`), bumping the mark's generation. New code that records Reports work must do the same, or the summary silently goes stale. A task that ends (`captureJobStatus` with a status that is not open: succeeded, failed, cancelled) marks the days of its current strings too, so its unfinished strings become abandoned; cancelling a native task records that status.
- `refreshSummaryDays` rebuilds a project's marked days from the raw records in one statement per table, under an advisory lock that is skipped when busy (or waited for a few seconds when asked), and clears a mark only if its generation did not change meanwhile.
- The summary refreshes at the end of each capture cron run: capture starts no new work after three minutes, and the refresh uses the time left up to four. A write never refreshes the summary itself.
- `ensureSummaryBuilt` queues every day of a workspace whose `reporting_workspaces.summary_version` is not `SUMMARY_VERSION`, for the first build and any later rebuild. `vp run reporting:summary rebuild` and `time` do the same locally.
- `reporting_workspaces.started_at` is each workspace's own Reports start, replacing `reporting_rollout` in the web app, set the first time Reports records anything for the workspace (and, since [the AI usage tab](./2026-10-27-reports-ai-usage-tab-design.md), at its first AI token row). Dates on the page start there. The `reporting_rollout` table itself stays, because go-svc's reporting routes still read it.
- Each analysis stores characters with and without spaces (grapheme clusters, from `countSourceCharacters`). Rows from before have none and show as "not counted".

### Reading

- Each tab has its own endpoint under `/api/orgs/:organizationSlug/reports`: `activity`, `step-times`, `ai-usage`, `words`, `time`, `costs`, `cost-estimate`, `budgets`, `rate-cards`, `tasks/:jobId/report` and `tasks/:jobId/analysis`, with `format=csv` where a table is shown. They are on the typed API client.
- Days are UTC. A headline number is compared with the previous period of the same length. Each figure has one name: Activity's cards are about the translation step (source words, which under a language filter are that language's arrivals; words to translate; finished; Progress, the share of the words that arrived finished so far, leaving abandoned strings out of what it divides by; and words reviewed, a count), and its chart has its own step switch; a task's Report tab shows its approved share as a snapshot of its own strings sent for review, its estimated cost for the whole task with each step's share, and the rate that priced each language; the Cost estimate tab counts "words in this estimate" by step. "Not priced" is shown where no rate applies at all, never $0.00. Word counts can be grouped by week and project, the volume each week.
- `GET /reports?report=activity|words|time|costs` (and `ai` since [the AI usage tab](./2026-10-27-reports-ai-usage-tab-design.md)) and the MCP `get_report` tool serve one of the page's reports with that tab's own fields, from the same reads (`report-reads.ts`), plus whether recent work is still being counted (`summary`, `stillUpdating`). The old raw-row report (`queryReport`) and the old page's routes (`/word-counts`, `/tasks/:jobId`, `/tasks/:jobId/match-analysis`, `POST /rates`) are removed.
- A cost estimate is for chosen tasks (1 to 50), or for the whole of one project from its current rows, priced by the project budget's card or the one chosen (a task's own card does not apply there).

### Who sees and changes what

- Reports are for `billing:read`: admins and localization managers. Every report, the public endpoint and the MCP tool refuse other roles. Changing rate cards, budgets and task pricing needs `billing:write`: admins.
- Other members keep their own time: the Reports page shows them only the Time tab with their own entries (no automated time), and a task's Report tab only the time logged on it; they can log, edit and delete their own entries.

### AI

- AI usage is tokens, calls, images and videos only, never money, by where the AI was called and by model. Revised by [the AI usage tab](./2026-10-27-reports-ai-usage-tab-design.md): its own tab, with finer groupings and billing's charge. A billing row's origin is its parent row's `source` (`dimensions.parent_operation_key`), or its own for a one-off call with no parent.
- A charge belongs to a task through its own `job_id`, its parent row's, or the connected TMS run its parent stands for, and then to that task's project only. With no task, it belongs to a project of the workspace recorded in its own or its parent's `dimensions.project_id`, else to its automation's project (for an automation's tool steps, the automation of the run named in their key, since [the AI usage tab](./2026-10-27-reports-ai-usage-tab-design.md)). An id that is not one of the workspace's projects is ignored: some tools record another system's project id under the same key. `ai-attribution.ts` is the one rule for AI usage and costs.
- AI money comes only from billing: `usage_events` rows with `feature_id = 'ai_tokens'` and `credential_source = 'gateway'`, summing `amount_usd`, from when Reports started for the workspace (since [the AI usage tab](./2026-10-27-reports-ai-usage-tab-design.md); before, Costs and Budgets counted billing's AI from before Reports started). Calls on a workspace's own key cost it nothing through us and are left out; rows without an amount yet are counted as pending. Reports' own AI cost rows are no longer priced or summed.

### Money

- **Spent** is people's work as recorded plus billed AI (expenses added by hand were removed on 2026-10-27; see the volume and steps record). A person's work is priced when it is finished, at the rate in force then: the task's own card as it was when the task was priced, else its project budget's card now, the same rule as the estimate, so pricing set on a task's Report tab after its strings arrived reaches what is spent; the unavailable band (the memory could not be read) is paid as new work, and the estimate says such a quote is not exact. A person's rewrite of text a job produced is dated by their save, not the job's day. Each charge counts once: on a task, outside tasks in a project, or, on the workspace's view only, outside any project. A budget's spent is all time, and says so.
- **Cost estimate** prices every current string of the chosen tasks (1 to 50) when the page reads it; nothing priced is stored.
- **Still to come** is the unfinished part of open tasks (queued, running, waiting for review) assigned to a person or marked payable, plus payable work outside any task.
- **Rate cards** are named sets of lines, one per language pair and step. Each line has its own basis (per word, per character, per character with spaces or per hour) and paid share per match band; the card has a default basis for new lines. Saving a card adds rows for changed lines and retired rows for removed ones, under a lock per card, so work already recorded keeps its rate. The unavailable band is paid as new.
- **Which card prices work:** the task's own card for the step, else the project budget's card, else the card chosen on the page. The first card found prices every language; a language it has no line for has no rate, with no fallback to the next card.
- **A task's own pricing** (`reporting_task_rates`, per step): a rate card, a time estimate and a fixed fee. The card is taken as it was at `priced_at`, set under the card's lock, so later changes to the card leave the task's prices alone. Pricing can change while the task is open and no work is recorded on that step (a finished string, a person's cost of work or a time entry; deleted ones aside; strings arriving do not count, since a task for people has them from creation, and nor do an agent job's AI calls). A fixed fee is charged once when the task succeeds (`captureJobStatus`); a task for people marked done by hand must set its status succeeded and `completed_at`, then record that status, for its fee to be charged and its saves to stop being matched to it. Pricing rows are deleted with the task.
- **A deleted task keeps its history.** Its analyses, finished work, costs and time entries keep its id (no link to `jobs`), so they stay the task's, shown as "Deleted task", as Crowdin, Phrase and Lokalise keep them; its unfinished strings leave Progress at the next rebuild of their days.
- Hourly lines share the task's time estimate evenly across the task's languages on hourly lines. A language filter leaves fixed fees out.

### Pages

- The Reports page, for the workspace and for each project, has six tabs: Activity, Word counts, Time, Costs, Cost estimate and Budgets (seven since [the AI usage tab](./2026-10-27-reports-ai-usage-tab-design.md)). The tab, dates and filters are kept in the address. The dates are one button that opens ready-made ranges (the last 7, 28 or 90 days, this month, last month, this quarter, since Reports started), which move with today, beside a two-month calendar (`react-day-picker`) and two typed boxes for fixed dates; days are UTC, from the day Reports started to today.
- Native tasks get a Report tab: their words, match analysis, time logged and, for `billing:read`, their cost and pricing. Native projects get a Reports link in their sidebar.

## Consequences

- On made-up data for 13 workspaces, a large workspace's reads take 0.01 to 0.27 seconds, against 2 to 7 seconds before. Budgets take 0.16 seconds; their AI spend reads all of a workspace's AI charges, so it grows with the workspace's history.
- By default the page lags the work by up to one capture run (2 to 17 minutes after a save).
- Refreshing rewrites the day's rows. Deleting a user leaves their work counted as a person's until the next rebuild of those days.
- A task for people is analysed and shown a few seconds after it is created; until then its Report tab says its strings are being counted and looks at the analysis's state every few seconds; a count that failed says so. Its untouched strings count in still to come from then on. A large file into many languages against a large memory takes minutes per language; the languages already recorded stay recorded if a later one is retried.
- Cancelling or failing a task takes its unfinished strings out of Progress at the next refresh of their days; deleting one does so at the next rebuild of those days, since deletion marks nothing.
- A change to a project budget's rate card applies to work not yet finished, as the estimate already shows it.
- A billed AI call that records no project counts only as AI outside any project.
- `reporting_task_rates.rate_id`, the old single rate line, and `reporting_analyses.rate_id`, the rate when a string arrived, are no longer read by the web app (go-svc's copy reads them) and stay as columns.
- go-svc's reporting routes (`apps/go-svc/reporting*.go`) follow the Reports API from before this rework: its old routes, one start for every workspace in `reporting_rollout`, and a task's pricing as one rate line (`rate_id`). They need moving to this design, or removing, before anything calls them.
- Local databases that applied the rework's interim migrations are brought in line with `bin/mark-migration-applied.sh` in hl-env, which rewrites Drizzle's bookkeeping only.

## Alternatives considered

- **Better indexes on the raw records.** Sections stayed at 2 to 7 seconds for a large workspace, since every finished-word total joins two large tables.
- **One all-time row per task.** Only 2.6 times fewer rows than the daily rows; most rows differ by language, band and payable flag, not by day.
- **Estimating a whole workspace or project.** 2.2 seconds for a large workspace. The estimate takes chosen tasks, as the design asked.
- **Reports' own AI price estimate.** It had no prices for the default models, and billing's charge is what the customer pays.
- **Falling back to the chosen card when the budget's card lacks a language.** The estimate would show a cost that recorded spending never would.
- **One rate line for all of a task's languages.** Prices every language at one language's rate.
- **Pricing a task only while it is queued.** Tasks people work on from the start are never queued, so they could never be priced.
