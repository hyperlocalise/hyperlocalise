# Reports: volume per week, time by task step, task run stages

**Status:** Accepted

Builds on [Reports rework](./2026-10-23-reports-rework-design.md) and follows [the AI usage tab](./2026-10-27-reports-ai-usage-tab-design.md). No migration; nothing new is recorded.

## Context

Users asked Reports for "weekly volume per project" and "time spent on each step". After the rework, volume per week was a table only (Word counts grouped by week), the Activity chart stacked finished words by where the text came from rather than by project, and time per step knew two steps, translation and review, so a post-edit task and a proofread task were one "Review" line. Automated run time showed each translation task run as one number from its first event to its last, with nothing about where the time went. The Costs tab also carried "expenses": a US dollar amount typed by hand against a project, from the first Reports (#2244), which no user asked for and no peer platform (Crowdin, Smartling, Lokalise, Phrase) offers.

## Decision

- **Expenses are removed** from the web app: the `POST /reports/expenses` route, the dialog, the Costs card and column and the CSV column. Spent on Costs and Budgets is people's work (`reporting_costs.kind = 'human'`) plus billed AI. The `reporting_costs` table keeps its `expense` kind because go-svc's copy of the old Reports API still writes it; the web app neither writes nor sums such rows.
- **A volume chart on Word counts, grouped by week.** `queryWordCountSeries` (`word-queries.ts`) reads the same daily summary table as the by-week table (the by-task table when tasks are chosen, still summed by project), one point per Monday-start UTC week from the week of the first day to the last, every week present. The five projects with the most units over the period are series of their own, the rest one "Other" series, as the AI usage chart does. It follows every filter the table follows (arrived or finished, unit, step, language, tasks, project). `readWords` adds it as `series` when `groupBy` is `week`, null otherwise, so `GET /reports/words`, `GET /reports?report=words` and MCP `get_report` carry it; the CSV is unchanged. The chart, its legend and its day labels are one component (`report-chart.tsx`) shared with the AI usage chart, which gains the year in its labels when a range spans two years.
- **Time by what each task is for.** Reports keeps `translation` and `review` as the steps it prices and records. A task's own step is worked out from the task (`taskStepSql` in `time-queries.ts`): `post_edit` for a proofread-kind job a visual workflow made with `workflowTaskStep = 'edit'` in its input payload, `proofread` for any other `proofread` or `review` job, `translate` for a translation job or a deleted task, and `other` for the rest (research, sync, asset jobs someone logged time on). "Time on each step" on Activity groups logged time by it, in that order; the Time tab's rows carry it in a "Task step" column beside the pricing step. The time CSV adds a `taskStep` column; the step-times CSV's logged rows now name the task step (`translate`, `post_edit`, `proofread`, `other`) where they named the pricing step. A time entry logged as review on a translate task counts as translate work, since the task is what people spend time on.
- **Task run stages.** `queryTaskRuns` (`time-queries.ts`) pivots each run's boundary events into four stages that mean the same for every file type: preparing, from `job_started` to `strings_extracted` (the sandbox, the file's strings and the glossary, guidelines and memory, which the workflow reads before extraction for text files and after it for Office and PDF files); reusing memory, to the last `translations_reused`; translating, to the last `locale_progress`, which the workflow records per language after each page that changed its count; finishing, to `job_succeeded` or `job_failed` (pages that changed nothing, any reassembly after a sandbox failure, rendering, writing and storing the translated files, the follow-up, the status). The languages' `locale_completed` events are written together after every file is stored, so they mark nothing per language and are not used. Each stage is clamped at zero and needs both its boundaries; a run's time outside the stages it has is "other", so without a language the stages sum to the run total shown before. Only runs with a `job_started` event count. With a language chosen on Activity, only runs that reached that language count; their reusing memory and translating are that language's own (from the memory reuse, the run's when the language had no reuse of its own, to its last progress), the other stages and the run total stay whole-run, "other" is zero, and the stages need not sum to the total. A language filled entirely from the memory has no progress event, so its translating is zero. The Step times table lists the stages with time under the run total, the run count on the total's row only; the CSV writes the task runs' row and a `task_run_stage` row per stage only when there were runs (before, the runs' row was always written). The Time tab's "Automated time" card still ignores the language, as its note says.

## Consequences

- A project's series is its name now; a renamed project keeps its history under the new name, and a project a viewer cannot open is not in the chart (the scope is the same as the table's).
- Post-edit and proofread still share the `review` rate line and the review half of every analysis; only time views tell them apart. Pricing post-editing differently from proofreading would need a third step through rates, analyses and summaries, with a migration.
- A task's step rests on the job's kind and on `workflowTaskStep`, which only `createWorkflowTaskJob` writes (the job creation route also spreads a caller's metadata, so an API caller can mark a proofread task as post-edit); a proofread task made another way that is for post-editing shows as proofread. A task's Report tab does not show its step; the task's title carries it ("Post-edit: …").
- Stage times are wall-clock between events languages share, so with several languages translating is the slowest language's time, not the sum. Translating ends at a language's last progress that changed its count, so pages that changed nothing and any reassembly after a sandbox failure, AI calls included, count as finishing. "Preparing" reads the glossary, guidelines and the file's strings; the translation memory is read in "reusing memory".
- Image and video runs record no stage events, so their time shows under "Other"; with a language chosen they count in the run total (their finished events name the language) with every stage at zero. A string job records only its failure and an email run nothing, so neither is counted; a file run that failed before any language event is left out when a language is chosen. Older file runs that recorded only `job_started`, `strings_extracted` and the end show preparing and finishing.
- `GET /reports/step-times` now takes `targetLocale` into the automated part; `GET /reports/time` does not, so the two can differ for the same dates while a language is chosen.
- Expense rows already recorded (by the web app until now, or by go-svc's copy of the old API, which still serves and sums them) leave Costs and budgets' spent, so a budget's state can change; nothing warns, since Reports has no users yet. `reportingStart` still takes the earliest cost row of any kind.

## Alternatives considered

- **A third pricing step for post-edit:** the full answer to "time per step", but a migration through every Reports table and the rate cards, for a distinction only time views need today.
- **A weekly chart on Activity instead of Word counts:** Activity's chart is by day or week depending on the range and stacks by text source; two stacked charts there would compete. The by-week table already holds the numbers, so the chart sits with it.
- **Keeping expenses with edit and delete added:** finishing a feature nobody asked for; removed instead, with the table kept for the Go copy.
- **Stages from `context_ready` and `locale_completed`** (preparing, extracting, reusing memory, translating, finishing, with a language's own time from its `locale_completed`): built first, then found to misread the workflow, which writes `context_ready` after extraction for Office and PDF files and every language's `locale_completed` together after the files are stored. Replaced by the four stages above; recording new boundary events in the workflow was left aside as a change to a shared system for a Reports view.
- **One stacked chart per tab:** the Word counts chart began as a copy of the AI usage chart; the shared component replaced both before either drifted.
