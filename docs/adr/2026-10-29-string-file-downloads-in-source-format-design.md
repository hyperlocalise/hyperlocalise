# String file downloads in their own format

## Problem

**Download translations** on the project files page returned flat key and value JSON for every string file that is not JSON, under the source file's extension. `messages-fr.csv` held JSON, so the download could not be used where the source file is used.

## Decisions

- The route `GET /api/orgs/{slug}/projects/{projectId}/files/translations/download` writes CSV, TSV, YAML, XLIFF, PO and POT, Qt `.ts`, `.strings`, `.stringsdict`, `.xcstrings`, TOML, INI, XML, RESX and RESW, properties, PHP, Fluent, Liquid, SVG and JS/TS module files into a copy of their stored source file (`loadProjectSourceFormatTranslationDownload`). Office, PDF and whole-file formats (images, video, and documents including HTML) are handled before this path; JSON, JSONC and ARB keep the JSON download, and Lottie and subtitles keep their own writers, which run after it.
- The Next.js server checks access and loads the data; a server-only go-svc route, `POST /internal/translation-files/render`, writes the file. Its body is a multipart form, like `/internal/pdf/apply` and `/internal/plaintext/apply`: the source file as a `source` part (up to the 25 MiB upload limit) and a `request` JSON part with the path, locales, translations and sentence source texts. Unknown parts and fields are ignored, so the web app can add fields first.
- Writing a file in its own format was chosen over running the CLI in a sandbox for each download, which needs no Go changes but takes 10 to 30 seconds and one sandbox per file.
- The template is the source version the keys were read from (the reconciled version). Keys last read from a version older than the template are not sent: reconciling stamps every key of a version with that version, so an older stamp means the template does not have the key (a GitLab sync hides such keys, with their translations, instead of deleting them). This applies only when the template is still the file's reconciled version; for a file never reconciled, or one reconciled again during the download, every ready translation is sent, as are strings added through the public API, and one that matches no key of the file makes the download fall back to JSON. Only ready translations are sent; other strings keep the source text. A string that ingest split into sentences is written only when every sentence is translated, so a string never mixes languages; a whitespace-only sentence keeps its source text. A sentence a job left as its source and nobody has reviewed yet counts as untranslated, as it does for the next translation job.
- `translationfileparser.MarshalTargetFromSource` picks the writer for the extension. Before writing it keeps only values whose key the source file has, matching a trimmed key back to the file's own key when exactly one file key trims to it, because ingest stores keys trimmed. go-svc reports how many translations matched no key (as `X-Hyperlocalise-Export-Warning-Count`); such a translation can also mean the file was read differently, for example a PO file last ingested by a CLI older than 1.13.5, whose context and plural keys had another shape, and the download falls back to JSON rather than leave those strings untranslated.
- The source file's own declarations win over the project's source locale: XLIFF `source-language`, xcstrings `sourceLanguage` and Qt `sourcelanguage` are kept.
- PO and POT are written by the CLI's own PO writer for the target locale, unchanged: the header gets the target's `Language` and `Plural-Forms`, and translated plural messages get that many forms, a form the source language lacks (Russian `few` and `many` from English) taking the `other` translation. A filled-in template downloads named `.po`; its header otherwise stays as the template has it (a `fuzzy` flag, `charset=CHARSET`), as `hl sync pull` writes it.
- A CSV or TSV gets its translations in the column ingest read the source text from (the `target`, `value` or `source` column, else the first column after the key), as for any other single-language file. Ingest reads no other column, so a file with one column per locale is not supported as such: its other columns are kept unchanged. Only Excel workbooks read locale columns.
- When a file should be written in its own format and cannot be (no stored source content, a source over 25 MiB, go-svc unreachable or without the route, or a writer error), the translations download as JSON named `.json`, the response carries `X-Hyperlocalise-Download-Fallback: json`, and the reason and format are logged. The download dialog then warns how many files came out as JSON. Downloads keep working during deploys and rollbacks, when go-svc and the web app run different versions.

## Not changed

- For these formats the public translation download (web and go-svc) and MCP still return JSON, still named with the source file's extension; `hl sync pull` rebuilds files from that JSON. GitHub and GitLab content sync do not send these formats back to the repository.
- The CLI keeps its own per-format switch in `apps/cli/internal/i18n/runsvc/output_marshal.go`, which go-svc cannot import; both call the same writers in `translationfileparser`. The CLI fills a CSV's target-locale column when the file has one, and its source-language choices differ from the ones above. No shared writer changes: downloads write each format exactly as `hl sync pull` does.
