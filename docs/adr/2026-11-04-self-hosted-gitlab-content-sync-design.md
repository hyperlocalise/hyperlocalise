# Self-hosted GitLab content sync

**Status:** Accepted

Ships as one pull request with the [project Sync panel](./2026-11-04-project-sync-panel-design.md): pull files from GitLab into a project, and deliver translations as one merge request. Builds on the [self-hosted GitLab connection](./2026-11-03-self-hosted-gitlab-connection-design.md) and changes one line of the [project content sync](./2026-09-11-project-content-sync-design.md) record: GitLab does not reuse the sandbox clone.

## Context

A workspace connected to its own GitLab server wants its locale files pulled into a project and translations sent back. The GitHub content sync clones the repository into a cloud sandbox, which can't reach a server on a company network or a developer's machine, and plain file sync doesn't need a clone. The GitHub sync is live and stays as it is.

Translations are edited here, so a repeat sync must not throw them away when the repository drops a key.

## Decision

### REST, through one narrow interface

- **Every GitLab call is a REST request**, never a clone. They all go through one request function in `lib/gitlab/client.ts`, so a relay or a fixed outgoing address can be added in one place.
- **Content sync speaks files and reviews, never a provider's terms.** `lib/agents/content-sync/content-sync-provider.ts` is the whole interface:
  - read side, built: `resolveBranchHead`, `listFiles` (a folder, recursively, at one commit), `readFile` (bytes at that commit);
  - write side, built: `commitFiles` (several files as one commit on a start commit, creating the branch there or rebuilding an existing one on it; a change may say whether the file exists so the writer needn't ask), `upsertReview` (open a review from a branch, or update the open one's description and target, never its title, so a reviewer's draft mark survives), `findReview` (the branch's review in any state, with its marks), `closeReview` (with a reason and the sync's mark, the earlier description kept underneath) and `deleteBranch`; the reader also gained `listCommitPaths` for the branch check.
  - Outside it: connection setup and tokens (`lib/gitlab/access.ts`), and incoming webhooks, which each provider turns into a run.
- **Checked on paper** that GitHub (contents, git trees, pulls), Bitbucket Cloud (src, commits with multiple files, pullrequests) and Azure DevOps (items, pushes, pull requests) can each do every method. Not built; not tested.
- The GitLab adapter is `lib/gitlab/content-sync-reader.ts` and `content-sync-writer.ts`. Every read in a run uses the commit the run started from; a missing file is its own error (`content_sync_file_not_found`), distinct from a missing repository, so delivery can tell "create" from "update".

### What a pull imports

- The sync settings name **where each language's files sit**: a path template under the provider folder with `{{locale}}` for the language code (`{{locale}}.json`, `{{locale}}/pages/*.html`). A code names a project locale the way the Contentful, Intercom, Webflow and HubSpot integrations match locales: the same tag (case and `_` aside), else the one project locale of that language (`fr` for `fr-FR`, `en-US` for `en`); two of the language would be a guess, so neither is taken. There is no per-sync code map, so the rule is the same everywhere. The placeholder is required; `**` is allowed only as a whole folder and at most twice, a name may hold at most two `*` or `{{locale}}`, and at most eight wildcards in all, so matching stays fast. The source locale's files are imported as source files. A file whose code is a target locale is a translation file, left for delivery. A file that matches neither is skipped. Nothing is guessed, so a translated file is never read as English, and a run that finds no source file fails rather than succeeding with nothing.
- The settings live in the existing sync configuration (`ContentSyncConfig`: `branch`, `pathTemplate`). GitLab is offered in the visual workflow **Content sync** step and in the project Sync panel, which run the same `executeContentSyncConfig`.
- The run waits for every imported file's ingest to finish, so delivery can rely on the keys being there. A file whose bytes are unchanged since the last run is not stored again, whatever the commit, as long as the last version is the sync's own and its ingest isn't still running from the last hour; its last ingest is waited for, and queued again if it never ran or failed. No parse and no source-upload automation runs for that. A version a newer upload superseded counts as finished.

- An import replaces the platform's source text with the file's, as every upload does; editing source text in the platform is a separate, later design.

### What a delivery sends

After the pull, `deliver-gitlab-translations.ts` writes one language file per imported source file and target locale to one branch per sync (`hyperlocalise/translations-<key>`, the panel's sync id or the workflow id) and opens or updates its merge request.

- **Built against the target, every run.** Existing language files are read from the commit the run read (only the ones the listing has, a few at once), and the branch is rebuilt as one commit on that commit (`start_sha` with `force`), the way the GitHub path force-pushes: a closed or merged merge request, a target that moved on, a changed branch setting or a hand commit on the branch never leaves it stale. Nothing is committed only when the branch is already exactly that: one commit whose parent is the target commit, whose own diff touches exactly these paths, with exactly this content (git blob ids from the branch listing, computed locally, SHA-1 or SHA-256 by the repository's id length). The branch's merge request is looked up in any state, the sync's own only (no forks'): an open one is updated (description and target, never the title, so a reviewer's draft mark holds) and linked; none, or a merged one, gets a new one. Each merge request carries a hidden fingerprint of its content (the paths and blob ids) in its description: one a reviewer closed stays closed, whatever the branch or the target has done since, as long as the run would send the same content; different content gets a new one. When nothing can be sent (nothing approved differs from the target any more, or what differs waits, can't be read or clashes) but the branch still exists, the open merge request carries text the run would not send now, so it is closed with a line saying why and a hidden mark, its earlier description kept underneath, and the branch is deleted; a merge request the sync closed never holds the next one back. A run with nothing new whose open merge request already carries this content's fingerprint leaves it untouched, so an hourly sync adds no notes to it.
- **Only what changes goes.** A file is sent when an approved text differs from the file's current value at that key, or the file is new and has approved text; a reformat alone is never sent. A key with no approved text keeps the repository's current text, keys only the language file has (a locale's extra plural forms) stay, numbers, booleans and nulls keep the language file's own values, and keys the sync hid because the repository dropped them are never written back. Strings the importer never keyed (context fields, excluded paths, empty text) are copied from the source. Indentation, byte-order mark and final newline follow the existing file, else the source.
- **Naming.** The language code is the one the repository already uses for that locale, an exact code first (`fr-FR` over `fr`). A locale with no file yet is named by the project's tag written the way the repository writes its regional codes (`en_US`, `pt-br`); where the repository has only bare codes, by the bare language when the project has one locale of it, else by the tag as written. A regional code in the repository stands for its own region, or for a bare project locale of its language, never for another region; two source files that differ only by their code are resolved to the exact one, else neither is imported. Two source files that name the same language file are both skipped and counted; so is a target locale of the source's language whose file would be the source file itself. A Flutter ARB file gets its own code in `@@locale`.
- **Shapes.** A JSON file is rebuilt from the source file's own nesting and arrays, keeping the language file's indentation, byte-order mark and line endings, so the next import reads the same keys; a list with an item that has no text is left as the repository has it and counted, since leaving one item out would shift the others' keys. Keys someone hid by hand are not text to translate: they keep the repository's value, else the source's, never send their approved text, and never hold a page or list back. A FormatJS catalog keeps each message's other fields; a language file kept as `{ id: text }` stays in that shape, and a compiled one counts as unreadable. An HTML page goes out whole once every segment that is text to translate is approved, and counts as held back before that. A Lottie animation, and every other format, counts as unsupported; a file whose source or repository copy can't be read as JSON counts as unreadable.
- **A refused write is an outcome, not a failure.** The pull has landed, so the run succeeds with the pull's report and `pushed.error` says why nothing was sent: a token without write access (the hint and docs say a read-only token pulls only), a project rule that refused the commit or merge request (400 or 422), or an unreachable server. The status is logged without names or paths.

### Keys the repository dropped

A GitLab sync hides them with the existing hidden flag, which translation jobs skip, instead of deleting them, and records that a sync hid them (`hidden_by_sync_at`). A key that comes back is unhidden only if a sync hid it (a hand upload that brings it back shows it too); hiding or unhiding by hand clears the record, so a key unhidden by hand while still missing is hidden again the next time its file is imported. A file the repository dropped has all its keys hidden the same way: only files this sync would import (under its project folder, matching its template as a source file) are considered, so a second sync's files under the same project folder are left alone as long as its template does not match them (two syncs with one project folder and templates that match each other's files hide each other's files in turn; D247), and a file the template no longer names is left as it is. A file that comes back unchanged is shown again without a new ingest. Every other upload path keeps today's delete, so a hand upload of a synced file removes the keys the sync had hidden.

### Reporting

The keys a run hid are stored on the source file version (`sync_report`); the run summary lists them per file. They are never written to key metadata, which several services rewrite without locking.

## Consequences

- A sync needs a workspace GitLab connection; a member's GitLab.com sign-in is not used, since runs have no user.
- The sync holds the GitLab project's id as well as its path, and refuses to run when the path on the current server names another project. The step's repository picker lists projects only when the workspace has a connection.
- A sync's waits for many files run together with one time limit; a very large folder may need more than one run. Two Content sync steps for the same repository that keep the default project folder write the same files; nothing stops that yet.
- A translation file in the repository is counted and left as it is until delivery; a manual clean-up of hidden keys is later work.
- Delivery sends approved translations as they stand. Whether a source text change should send a key's approved translations back to review is a separate decision for every upload path, with its own design record; today they stay approved, as the [reconciliation design](../plans/2026-09-13-source-file-reconciliation-design.md) and the guide on updating source content say.
- The GitHub content sync still clones, delivers unreviewed text and hard-deletes missing keys. Moving it onto the interface is a separate change.
