# Reports reads and writes in go-svc

**Status:** Accepted

Moves the Reports API ([Reports rework](./2026-10-23-reports-rework-design.md)) from the web app's Hono routes to go-svc, one slice at a time, then switches the page over. Recording (analyses, finished strings, job status, pricing at finish, AI costs), word counting, the memory matcher and the 15-minute capture cron stay in the web app.

## Context

- go-svc held a copy of the old Reports API (`apps/go-svc/reporting*.go`, from before the rework), as step one of the usual move: copy into Go, then switch the page over. The rework replaced the design it copied, so nothing called it.
- Reports' reads and writes are about 4,200 lines of TypeScript, most of it SQL, which ports line for line. Reports has no customer users yet and sits behind the `workspace-reports` flag.
- go-svc's size in production (vCPU, memory, pool size) is not stated anywhere in the repo. Its pool is the pgx default, and the glossary routes already work around it running out.

## Decision

- **The Go routes answer as the web routes do:** the same paths under `/v1/orgs/{slug}/reports`, query fields, error codes, answer shapes and permissions, plus a `message` on errors as every go-svc API gives. Each section ports with its web test cases.
- **Layout.** `reportingAPI` (`reporting.go`) follows the other go-svc areas: its own actor, failure type and `handle` wrapper, registered from `handler.go`, wired in `main.go`. The wrapper checks the session, the workspace, the flag and the route's capability in that order, as the web middleware chain does. Shared files get a few lines each (a field, the registration, the wiring, the request-log path); the old `workspaceHandle` no longer special-cases CSV.
  - `reporting-access.go`: the viewer's projects by the team rule, when Reports started, the request context.
  - `reporting-period.go`, `reporting-query.go`, `reporting-scope.go`, `reporting-csv.go`: the dates, query parsing that refuses what the Zod schemas refuse (lengths in UTF-16 units, repeated keys, empty values), the summary rows a section reads, and streamed CSV with the web app's cell quoting.
  - One file per section: `reporting-settings.go`, `reporting-activity.go`, `reporting-tasks.go` (the task picker), `reporting-time.go` (the Time tab and time by step), `reporting-words.go` (the Word counts table and chart), `reporting-costs.go` (costs, the estimate, what is still to come, budgets), `reporting-ai.go` with `reporting-ai-attribution.go` (AI usage and where each billing row belongs), `reporting-rate-cards.go` (the list and the save), `reporting-task-report.go` (a task's report and analysis state), `reporting-task-pricing.go` and `reporting-time-entries.go` (the writes). Writes run in `api.write`: the same admission slot and statement limit as a read, one transaction, the web app's locks byte for byte (the task row for pricing and time, the card's advisory lock for a save and for pricing by a card) and the same `reporting_audit` rows, with the rows before and after shaped as the web app records them.
  - `reporting-internal.go`: `POST /internal/reports/{kind}` for the MCP `get_report` tool, behind the service token, answering for the member the caller names with that member's own access. The web's combined `GET /reports?report=…` route is not ported: nothing reads it (the tool calls the read functions directly, and moves to the internal route). Kept from the old copy for the later slices: `reporting-money.go` (fixed-point USD arithmetic) and the `reportingBody` JSON parser in `reporting.go` (the writes). The old copy's `loadReportingJob` went unused once the task report and time entries loaded tasks their own way, and was removed.
- **Safeguards for an unknown service size** (`reporting-safeguards.go`), all inside Reports' own code: at most 2 Reports requests query the database at once per copy; each read runs on one pooled connection in a read-only transaction with a 10 s statement limit (the MCP route's words report runs three); CSVs are written row by row; the flag answer is cached per workspace and user for a minute, requests that miss together share one lookup, and a failed lookup is never cached. Under load this makes the Reports page slower, not editor saves.
- **Verification.** While both route sets exist, a comparison harness (on the port branch only, never on main: a fixed seed, a request list, both sides answered in-process with the same stubbed session and flag, compared field by field) proves each ported route. Lasting coverage is the ported Go tests.
- **Defects fixed in the port** (each small, by the plan's rule): the task picker offers tasks Reports has not counted when asked (`counted=false`), so time can be logged on them once the page uses it (D160's server half). Starting the period no earlier than the day Reports started (D194) was tried and reverted in review: it collapsed a range wholly before the start to one day and hid time logged on earlier days; D194 stays open for a bar cap instead.
- **Verification of writes.** The harness compares a write by the rows it leaves: each write request names a check query both sides run afterwards, returning one JSON document with generated ids masked (a rate line named by its card, language and rate instead of its id), and the answer's own generated ids are ignored by pattern.
- **Slices.** Reads first (this record), money reads with the MCP route, the writes, then the page switch, then the Hono routes removed one release later; the columns only the old Go copy read (`reporting_analyses.rate_id`, `reporting_rollout`) and `reporting_task_rates.rate_id` (still returned in the task pricing answer, as the web returns it, so that answer changes with the column) are dropped last.

## Consequences

- Nothing calls the Go routes until the page switches, so slices merge as they are reviewed.
- The web app's Reports routes are unchanged until the switch; changes to them are paused meanwhile, and a Reports change made in TypeScript during the port must be ported too.
- The harness cannot check cross-workspace access or the flag itself, since both sides stub them; the Go tests cover those.
- The two-at-a-time limit is per copy of the service and shared by every workspace, so one workspace's slow requests delay the others' on that copy; a limit per workspace is the next step if Reports gains users before go-svc's size is known.
- For the page switch: CSV downloads must fetch with the token and save (a plain link cannot sign in to go-svc) and show a `report_timed_out` answer; the page should retry only 503s and fewer times; the MCP tool keeps its own validation (the route answers only a code) and may pass numbers and booleans in `query`.
- Names (rate cards, projects in Costs and Word counts) are ordered by the root collation (`golang.org/x/text/collate`, a pool of collators since one is not safe for concurrent use), which is what the web's `localeCompare` (run in Node, on the server) uses. The task report CSV rounds money as the web's `toFixed(2)` does, on the double, so the cells match the web's to the cent.
