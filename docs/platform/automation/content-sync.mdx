---
title: "Sync content with GitHub"
description: "Move source files into Platform and return ready translations to a GitHub repository."
---

Content sync moves files between a connected source and a native project. **GitHub is the executable content-sync provider currently supported.** Other provider choices may appear in setup, but their content movers are not available yet.

Connecting GitHub gives Platform access to repositories. It does not start a file sync or generate translations.

## Configure content sync

1. [Connect GitHub](/platform/connections/github) and enable the intended repository.
2. Open the project’s **Automations** page.
3. Select **Add content sync**.
4. Choose the GitHub resource and the source/project folders.
5. Review the mapping and enable **Sync content**.
6. Inspect the run and confirm the source paths in **Files**.

Pull brings source content into the project folder. Push sends translations that are already ready back to GitHub through a pull request. Review that pull request before merging it.

## Pull from a self-hosted GitLab server

A workspace connected to its own GitLab server can pull a repository's source files into a project with the visual workflow **Content sync** step. Delivering translations back as a merge request is coming next.

1. Connect the server under **Integrations**. Runs use the workspace's connection, not a member's GitLab.com sign-in.
2. In a visual workflow, add a **Content sync** step, choose **GitLab** as the source and pick the repository.
3. Set the provider folder, the project folder, and **Language file paths**: where each language's files sit under the provider folder, with `{{locale}}` standing for the language code, for example `{{locale}}.json` or `{{locale}}/pages/*.html`. Only the source language's files are imported. If the repository names a language differently from the project, add it under **Language codes in the repository**, one per line, such as `fr-FR = fr`.
4. Leave **Branch** empty to read the repository's default branch.

Each run reads the branch's latest commit. A file whose content hasn't changed since the last run is skipped. Keys the repository no longer has, and whole files it dropped, are hidden in the project, not deleted, so their translations stay and translation jobs skip them; a key that comes back is shown again.

By default the repository's source text replaces the project's on every run. To edit source text in Hyperlocalise as well, turn on **Edit source text in Hyperlocalise** in the project's settings. A run then keeps edits made here, takes changes made in the repository, and reports a key as a clash when both sides changed it differently, keeping the project's text. The step's output lists the clashes and the hidden keys per file.

## Connect the translation step

Content sync itself does not create translation jobs. Add a [Source upload automation](/platform/automation/create-automation) or [request a translation](/platform/translation/start) after the source arrives. Review the translations before the next outbound sync.

Use a small test file to verify the full sequence: source arrives, translation runs, review completes, and the expected target path appears in a pull request.

## Avoid duplicate delivery

Decide whether Platform content sync or your CLI/CI workflow owns a given source-to-target mapping. Running both for the same paths can produce competing updates. Keep the repository branch and locale paths consistent across the chosen workflow.

For troubleshooting, distinguish connection access, sync errors, generation errors, and review readiness. See [Automation troubleshooting](/platform/help/automations) and the [GitHub workflow tutorial](/platform/tutorials/github-localisation-workflow).
