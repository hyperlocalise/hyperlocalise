Use this API to upload source files, create translation jobs, check progress, and retrieve translated files. It is also the API used by [Platform CLI sync](/platform/cli).

For identity, project discovery, and Queries, use the separate [Projects and Queries API](/platform/developers/projects-and-queries). See [Choose an API](/platform/developers/api-overview) for base URLs and authentication. The OpenAPI document for that API does not describe these file and job routes.

## Base URL

```
https://hyperlocalise.com/api/v1
```

The CLI `hyperlocalise.api_base_url` default is `https://hyperlocalise.com/api`. Paths below are relative to that host, including `/v1`, except job reads.

Read jobs from `https://public-api.hyperlocalise.com/v1`. See [Read jobs](#read-jobs).

## Authentication

Create a key under **Settings** → **API Keys**. Send it on every request:

```
x-api-key: <secret>
```

Missing, invalid, or revoked keys return `401` with `error: "unauthorized"`. An archived workspace returns `403` with `error: "workspace_archived"`.

### Permissions

| Permission | Used by |
| --- | --- |
| `files:write` | Upload a source file, and send a translation as another project's source |
| `files:read` | Download a stored file, reconstructed translation, or image variant |
| `jobs:write` | Create a translation job or a key job, and complete a task for people |
| `jobs:read` | Read job status, latest job for a source path, and match-band analysis |
| `memories:read` | Export translation memory entries as TMX or CSV |
| `memories:write` | Import translation memory entries from TMX or CSV |

Omitting `permissions` grants every scope the key owner can hold. Localization operators receive all six. Job contributors receive every scope except `memories:write`. Members receive `jobs:read`, `files:read`, and `memories:read`.

A key only sees projects the key's creator can access.

## Errors

JSON errors use this envelope:

```json
{
  "error": "machine_readable_code",
  "message": "Human-readable description"
}
```

Branch on `error`. `message` is for debugging and may change. File downloads return the raw body instead of JSON.

## Files

### Upload a source file

`POST /v1/files`

Permission: `files:write`

`multipart/form-data`. Maximum body size is 25 MiB.

| Field | Required | Notes |
| --- | --- | --- |
| `file` | yes | The source file bytes |
| `projectId` | yes | Platform project id |
| `sourcePath` | yes | Repository-style path, max 2048 characters |
| `sourceHash` | no | |
| `commitSha` | no | |
| `workflowRunId` | no | |
| `sourceLocale` | no | |
| `format` | no | |
| `branch` | no | |
| `keepApproved` | no | `true` keeps approved translations approved for this upload's source text changes, in a project whose **When source text changes** setting is **Needs review**. Native projects only. See [Update source content safely](/platform/guides/update-source-content#skip-the-review-for-a-small-fix). |

`201` response for a native project (resource-keyed):

```json
{
  "file": {
    "id": "file_...",
    "sourceFileVersionId": "...",
    "filename": "en.json",
    "contentType": "application/json",
    "byteSize": 128,
    "sha256": "...",
    "destination": "native"
  }
}
```

TMS-backed projects return `destination: "external_tms"` plus provider fields instead of the stored-file metadata.

This is the same upload `hyperlocalise sync push` performs. It does not create a job.

### Download a stored file

`GET /v1/files/{fileId}/download`

Permission: `files:read`

Returns the file bytes with `Content-Type` and `Content-Disposition`.

### Use a translation as another project's source

`POST /v1/projects/{projectId}/files/translation-source`

Permission: `files:write`, and a role that can manage projects (admin, localization manager or developer) with access to both projects

The same action as **Use translation as source…** on the Files page. It builds a Word or Excel file of project `projectId` from its approved translations in the other project's source language, and uploads it to the other project as a source file under the same path. An `.xls` file arrives as `.xlsx`. The other project's source language must be one of this project's target languages. See [Translate through another language first](/platform/projects/files#translate-through-another-language-first) for how the two projects work together.

```json
{
  "sourcePath": "requests/report.docx",
  "destinationProjectId": "project_456",
  "replaceVersionId": "8d6c0f0e-..."
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `sourcePath` | yes | The file's path in project `projectId` |
| `destinationProjectId` | yes | The project to send it to |
| `replaceVersionId` | no | The other project's file version at that path to replace, from a `destination_file_replaced` refusal |

`201` response, with the file's path in the other project:

```json
{
  "file": {
    "destinationProjectId": "project_456",
    "sourcePath": "requests/report.docx",
    "sourceFileVersionId": "...",
    "stringCount": 42
  }
}
```

A send reads the file from this project's default branch, `main`, and uploads it to the other project's `main` branch; there is no `branch` parameter. Files at the same path on other branches are left alone.

Sending the file again updates the same strings in the other project. A send replaces the other project's file at that path without asking only when that file came from this file's last send. Anything else there, such as a file uploaded by hand or added by a repository sync, is refused with `destination_file_replaced`; `details.destinationFile` says what it is:

```json
{
  "error": "destination_file_replaced",
  "message": "...",
  "details": {
    "destinationFile": {
      "path": "requests/report.docx",
      "versionId": "8d6c0f0e-...",
      "addedAt": "2026-11-13T02:10:00.000Z",
      "addedBy": "Ana Silva",
      "addedThroughApi": false,
      "fromRepositorySync": false,
      "sentFrom": null
    }
  }
}
```

To replace it, send again with its `versionId` as `replaceVersionId`. If another file arrives there in the meantime, the send is refused again with the new version. `addedBy` is the person who uploaded the file, or the owner of the API key that did, when `addedThroughApi` is `true`. It is `null` when that is not known, for example for a removed member. `destinationFile` is `null` when the file there changed again while the refusal was made; send again as before. `sentFrom` names the project and path a file sent from elsewhere came from; `projectId` and `projectName` are `null` when the key's owner cannot open that project. A file from a repository sync may be stored again by the sync's next run.

Refusals:

| Status | `error` | When |
|---|---|---|
| 400 | `invalid_translation_as_source_payload` | The body is not valid |
| 400 | `unsupported_file_format` | The file is not a Word or Excel file |
| 400 | `same_project`, `project_not_native` | The other project is this one, or either project is in a connected TMS |
| 400 | `locale_not_a_target`, `destination_source_locale_mismatch` | The other project's source language is not one of this project's target languages |
| 403 | `forbidden` | The key lacks `files:write`, or its owner's role cannot manage projects |
| 404 | `project_not_found`, `destination_project_not_found`, `source_file_not_found` | Not found, or the key's owner cannot open it |
| 409 | `translations_not_approved` | Some strings have no approved translation in that language. `details` has `missingCount`, `totalCount`, and up to 20 `missingStrings` (`key`, `sourceText`) |
| 409 | `destination_file_replaced` | The other project has a file at that path this file did not send (above) |
| 409 | `destination_branch_protected` | The other project's `main` branch is protected |
| 409 | `source_file_not_ready` | The file's newest upload is still being read. Try again shortly |
| 422 | `source_file_read_failed` | The file's newest upload could not be read. Upload it again |
| 422 | `no_strings`, `file_cannot_be_written`, `file_reads_differently` | The file cannot be sent as it is |
| 500 | `file_build_failed`, `upload_failed` | Try again |

To send a file once its translation is finished, listen for the job-change [webhook](/platform/developers/webhooks) on its review job (`job.status_changed` to `succeeded`), then send the file under the path it was uploaded with. A finished review job does not mean every string is approved: if some are not, the send is refused with `translations_not_approved`, and can be sent again once they are.

## Jobs

### Create a job

`POST /v1/jobs`

Permission: `jobs:write`

JSON body. Discriminate on `type`.

**String job**

```json
{
  "type": "string",
  "projectId": "project_123",
  "stringInput": {
    "sourceText": "Save changes",
    "sourceLocale": "en-US",
    "targetLocales": ["fr-FR"],
    "context": "Primary toolbar button",
    "maxLength": 24
  }
}
```

**File job**

```json
{
  "type": "file",
  "projectId": "project_123",
  "fileInput": {
    "sourceFileId": "file_...",
    "fileFormat": "json",
    "sourceLocale": "en-US",
    "targetLocales": ["fr-FR"]
  }
}
```

`sourceFileId` must already exist in the project (upload first). Locales must match the project. `201` response:

```json
{
  "job": {
    "id": "job_...",
    "type": "file",
    "status": "queued"
  }
}
```

**Key job**

A task for people on a chosen set of strings, picked one way only: `stringIds`, `keys` (key names, in any file), or `tags` (strings carrying every tag when the job is created). Up to 5,000 strings; hidden strings and strings in no file are left out. A key job runs no AI translation and is never queued: it starts as `waiting_for_review` for people to translate and review in the Content Editor.

```json
{
  "type": "keys",
  "projectId": "project_123",
  "title": "Release 7 checkout",
  "keysInput": {
    "sourceLocale": "en-US",
    "targetLocales": ["fr-FR", "de-DE"],
    "keys": ["checkout.title", "checkout.pay"]
  }
}
```

A key job's `201` response has `"type": "keys"` and `"status": "waiting_for_review"`.

#### Title, deadline and owner

Every job type takes these optional top-level fields:

| Field | Type | Notes |
|---|---|---|
| `title` | string, 1–256 | Shown as the job name in the app |
| `description` | string, up to 2,048 | Shown on the job |
| `dueAt` | ISO 8601 date-time with offset | For example `2026-11-15T17:00:00Z`. A date without a time zone is rejected |
| `ownerEmail` | email | Must belong to a member of the workspace. Matched without regard to case. The member becomes the job's owner |

```json
{
  "type": "file",
  "projectId": "project_123",
  "title": "Spring campaign – landing page",
  "description": "Marketing review before Friday",
  "dueAt": "2026-11-15T17:00:00Z",
  "ownerEmail": "pm@example.com",
  "fileInput": {
    "sourceFileId": "file_...",
    "fileFormat": "json",
    "sourceLocale": "en-US",
    "targetLocales": ["fr-FR", "de-DE"]
  }
}
```

[Get a job](#get-a-job) and [latest job](#latest-job-for-a-source-path) return `title`, `description`, `dueAt` and `ownerEmail`, `null` when unset.

#### Retries with `Idempotency-Key`

Send an `Idempotency-Key` header to make retries safe. The key is 1–255 printable ASCII characters with no spaces, unique within the workspace. Prefix it with your integration name, for example `orders:1042`.

- A retry with the same key and the same request creates nothing. It returns `200` with the job the first request created, its current `status`, and the header `Idempotent-Replayed: true`.
- Owner email is matched without regard to case. `dueAt` values that name the same instant, and metadata objects that differ only in key order, count as the same request.
- If the first request created the job but could not enqueue it (`503 job_queue_unavailable`), a retry with the same key tries to enqueue that job again.
- The same key with a different body returns `422` `idempotency_key_reused`.
- Requests sent at the same time with one key create one job.

```bash
curl --fail-with-body "https://hyperlocalise.com/api/v1/jobs" \
  -H "x-api-key: $HYPERLOCALISE_API_KEY" \
  -H "Idempotency-Key: orders:1042" \
  -H "content-type: application/json" \
  -d @job.json
```

| Status | `error` | When |
|---|---|---|
| 400 | `invalid_job_payload` | Body does not match the schema, including a `dueAt` without an offset |
| 400 | `owner_not_found` | `ownerEmail` is not a workspace member |
| 400 | `invalid_idempotency_key` | Empty, too long, or not printable ASCII |
| 422 | `idempotency_key_reused` | Key already used with a different body |
| 400 | `no_strings_matched` | A key job's selection matches no visible string |
| 400 | `too_many_strings` | A key job's selection matches more than 5,000 strings |
| 409 | `project_not_native` | A key job names an external TMS project |
| 503 | `job_queue_unavailable` | The job was created but not enqueued. Retry with the same key |

### Complete a task for people

`POST /v1/jobs/{jobId}/complete`

Permission: `jobs:write`

Finishes an open task for people, such as a key job or a proofread job, the same way **Mark done** does in the app. Reviewers, localization managers, and admins can complete any such task; anyone else only a task assigned to them. A completed task can't be reopened.

```json
{ "job": { "id": "job_...", "status": "succeeded" } }
```

| Status | `error` | When |
|---|---|---|
| 403 | `forbidden` | The task is assigned to someone else, or your role can't change jobs |
| 404 | `job_not_found` | No such job in a project you can access |
| 409 | `job_action_unavailable` | The job is not an open task for people |

The CLI does not call these endpoints during `sync push`. Platform automations and the UI create jobs after upload.

After you create a key job, list its strings, add or remove keys, read per-locale progress, and change target languages on `https://public-api.hyperlocalise.com/v1`. See [Strings and key jobs](/platform/developers/strings-and-key-jobs#key-jobs-after-creation).

### Read jobs

Job reads use a different host from the rest of this API:

```
https://public-api.hyperlocalise.com/v1
```

Send the same `x-api-key`. `https://hyperlocalise.com/api/v1` no longer serves these routes.

### Latest job for a source path

`GET https://public-api.hyperlocalise.com/v1/jobs/latest?projectId={projectId}&sourcePath={sourcePath}`

Permission: `jobs:read`

Returns the most recent succeeded file job for that source path, including `outputFiles`.

### Get a job

`GET https://public-api.hyperlocalise.com/v1/jobs/{jobId}`

Permission: `jobs:read`

```json
{
  "job": {
    "id": "job_...",
    "projectId": "project_123",
    "type": "file",
    "status": "succeeded",
    "createdAt": "...",
    "updatedAt": "...",
    "completedAt": "...",
    "lastError": null,
    "title": "Spring campaign – landing page",
    "description": null,
    "dueAt": "2026-11-15T17:00:00.000Z",
    "ownerEmail": "pm@example.com",
    "outputFiles": [
      { "fileId": "file_...", "locale": "fr-FR", "filename": "fr.json" }
    ]
  }
}
```

### Job status

`GET https://public-api.hyperlocalise.com/v1/jobs/{jobId}/status`

Permission: `jobs:read`

Smaller payload with `id`, `projectId`, `kind`, `type`, `status`, timestamps, and `lastError`.

```bash
curl --fail-with-body "https://public-api.hyperlocalise.com/v1/jobs/$JOB_ID/status" \
  -H "x-api-key: $HYPERLOCALISE_API_KEY"
```

### Match-band analysis

`GET https://public-api.hyperlocalise.com/v1/jobs/{jobId}/analysis`

Permission: `jobs:read`

Returns the job's units by target locale, step, and translation memory match band. These are the same counts as the job's **Report** tab in [Reports](/platform/workspace/reports).

Optional query: `unit` is `words` (default), `strings`, `characters`, or `characters_with_spaces`.

```json
{
  "analysis": {
    "jobId": "job_...",
    "unit": "words",
    "bands": ["repetition", "100", "95-99", "85-94", "75-84", "50-74", "new", "unavailable"],
    "steps": [
      { "step": "translation", "status": "done", "incomplete": false, "updatedAt": "..." }
    ],
    "locales": [
      {
        "targetLocale": "fr-FR",
        "step": "translation",
        "total": 50,
        "bands": {
          "repetition": 0, "100": 12, "95-99": 0, "85-94": 8,
          "75-84": 0, "50-74": 0, "new": 30, "unavailable": 0
        }
      }
    ]
  }
}
```

- `bands` lists every band in order. Each locale row includes all of them, `0` when empty.
- `steps[].status` is `pending`, `done`, or `failed`. An analysis that stays `pending` for more than an hour reads as `failed`.
- `incomplete: true`, or words in `unavailable`, means the translation memory could not be read for some strings, so those strings have no match band.
- `steps` and `locales` are empty until the job has been analysed.
- Money, rate cards, and cost estimates are not included.

```bash
curl --fail-with-body "https://public-api.hyperlocalise.com/v1/jobs/$JOB_ID/analysis?unit=words" \
  -H "x-api-key: $HYPERLOCALISE_API_KEY"
```

## Translation memories

TMX import and export use the same host as job reads:

```
https://public-api.hyperlocalise.com/v1
```

Send the same `x-api-key`. These routes wrap the native workspace memory the owner can already see. They do not create memories or list them.

### Export entries

`GET https://public-api.hyperlocalise.com/v1/translation-memories/{memoryId}/entries/export?format=tmx`

Permission: `memories:read`

Returns TMX 1.4 bytes (`application/x-tmx+xml`). Pass `format=csv` for the Hyperlocalise row layout. Optional `sourceLocale` and `targetLocale` filter to one language pair.

```bash
curl --fail-with-body "https://public-api.hyperlocalise.com/v1/translation-memories/$MEMORY_ID/entries/export?format=tmx" \
  -H "x-api-key: $HYPERLOCALISE_API_KEY" \
  -o product.tmx
```

### Import entries

`POST https://public-api.hyperlocalise.com/v1/translation-memories/{memoryId}/entries/import`

Permission: `memories:write`

JSON body. Inline TMX (or CSV) is applied immediately.

```json
{
  "format": "tmx",
  "content": "<?xml version=\"1.0\"?><tmx version=\"1.4\">...</tmx>"
}
```

`201` includes `imported`, `skipped`, and the import report. Units with a stable `tuid` upsert.

Large files can use `POST .../entries/import/uploads` to receive a signed upload URL, then `POST .../entries/import` with `attemptId` to apply. `GET .../import-attempts/{attemptId}` and `GET .../import-attempts/{attemptId}/download` read the attempt and its source file (`memories:read`).

### Copy from a connected TMS

Requires an active Crowdin, Phrase Strings, or Smartling connection (the credential updated most recently in the workspace).

List provider translation memories:

`GET https://public-api.hyperlocalise.com/v1/orgs/{organizationSlug}/tms/translation-memories`

Import into a native memory (background TMX export + interchange queue):

`POST https://public-api.hyperlocalise.com/v1/orgs/{organizationSlug}/translation-memories/{memoryId}/entries/import/from-tms`

Body: `{ "credentialId": "<uuid>", "externalId": "<provider id>" }`. Response `202` includes `attemptId`.

Glossary listing and `POST .../glossaries/{glossaryId}/concepts/import/from-tms` follow the same pattern; see [Glossary import and export](/platform/glossary-import-export#public-api-tms-copy).

## Translations and images

These reconstruct current project state. They do not require a job id. That is what `sync pull` uses.

### Download a reconstructed translation

`GET /v1/projects/{projectId}/translations/download?sourcePath={sourcePath}&locale={locale}`

Permission: `files:read`

Returns the translated file bytes for that source path and target locale.

To export only the segments that match Content Editor filters (CSV, TMX, XLIFF, XLSX), use **Download** in the [Content Editor](/platform/cat) queue—not this endpoint.

### Download an image variant

`GET /v1/projects/{projectId}/images/download?sourcePath={sourcePath}&locale={locale}`

Permission: `files:read`

Returns the localized image variant when one exists for that path and locale.

## Example

Upload a source file with curl:

```bash
curl -X POST "https://hyperlocalise.com/api/v1/files" \
  -H "x-api-key: $HYPERLOCALISE_API_KEY" \
  -F "projectId=project_123" \
  -F "sourcePath=locales/en-US.json" \
  -F "file=@locales/en-US.json"
```

Send a Word file's approved English to the English project:

```bash
curl -X POST "https://hyperlocalise.com/api/v1/projects/project_123/files/translation-source" \
  -H "x-api-key: $HYPERLOCALISE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"sourcePath":"requests/report.docx","destinationProjectId":"project_456"}'
```

Download the French reconstruction:

```bash
curl -L "https://hyperlocalise.com/api/v1/projects/project_123/translations/download?sourcePath=locales/en-US.json&locale=fr-FR" \
  -H "x-api-key: $HYPERLOCALISE_API_KEY" \
  -o locales/fr-FR.json
```
