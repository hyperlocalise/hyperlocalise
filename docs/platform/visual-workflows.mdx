title: "Visual workflows"
description: "Connect typed data between workflow nodes, test drafts safely, and publish automation versions."

Visual workflows compose fixed automation steps on a canvas. Open **Automations → Visual workflows** to create or inspect a workflow. If it is unavailable, ask your administrator or [support](/platform/help/contact-support) about workspace access.

## Build and connect data

1. Choose a manual, scheduled, GitHub, source-upload, **Webhook**, or [**Job changed**](/platform/developers/webhooks#start-automations-on-job-changes) trigger.
2. Add HTTP, AI, Slack, email, condition, switch, Set, object and JSON steps, For each, Array transform, Sequence, Retry, or **Call workflow** nodes.
3. Connect execution order on the canvas.
4. Select a node. Its settings open on the **Configuration** tab. A setting that can take its value from an earlier step shows a port mark beside its name: type a value, insert fields from earlier steps by typing `{{` or with the braces button beside the box, or wire the port on the canvas. An inserted field shows as a pill naming its step and field; a red pill names a step that does not run before this one. Backspace removes a pill whole. On the canvas, each pill draws a thin dashed line from the field it reads to the setting's port; it cannot be selected or moved. Data wires are thin solid lines, and the connections that decide the order steps run in are thicker. A wired setting shows which step feeds it.
5. Review the **Outputs** tab for expected fields. Test results show actual redacted values.

Direct field bindings preserve objects, arrays, numbers, booleans, and null. Templates produce text, for example `Summary: {{ nodes.summarize.text }}`. A reference in a setting's text starts with `trigger` or `nodes`; any other, such as `{{ item.name }}`, cannot be read by a run, so the step lists it as an issue and the workflow cannot be published until it is fixed. Missing required values stop the action. Fields from a conditional branch need an optional binding or fallback because that branch may be skipped.

HTTP JSON responses have an unknown shape until you declare output fields such as `json.items` with type `array`. Samples help discover fields but do not guarantee their presence. HTTP bodies can be structured JSON; binding resolution happens before serialization, so quotes and line breaks remain valid JSON. AI nodes can declare structured `json.*` output fields.

## Loops and branching

**For each** requires an array. Connect **Each item** to the body and **Done** to the next step; the steps wired from **Each item** form the body. Body nodes can read the loop's `item` and `index`: wire them, or write them in a setting's text through the loop step, as `{{ nodes.<loop step id>.item.<field> }}`. Configure collected output bindings to expose `iterationOutputs` after the loop. Items run sequentially; an empty array follows Done with an empty result. Nested loops are not supported.

**Array transform** applies **Filter**, **Map**, **Reduce**, or **Find** to an ordered collection. Connect **Each item** to the body and **Done** to the next step, then collect a `result` binding from the body. Filter and Find require a boolean body result. Map and Reduce use the declared result type. Reduce also needs an initial value. Body nodes can read `item` and `index`, plus `accumulator` during Reduce. After **Done**, Filter and Map expose `items`, Reduce exposes `value`, and Find exposes `found` with an optional `value`. Collections are limited to 100 items, and nested collection regions are not supported.

**Sequence** runs multiple downstream paths in a fixed order. Add named outputs on the node, connect one path to each output handle, and list the outputs in the order they should run. The workflow finishes the first path completely before starting the next. Use it when later steps must wait for earlier paths to finish, for example sending Slack before email.

**Retry** wraps steps that may fail with transient errors. Connect **Attempt** to the steps to retry; the steps wired from **Attempt** form the body, as with **For each**. Connect **Succeeded** to the step that runs when the body finishes without a retryable failure, and **Exhausted** to the one that runs when all attempts are used. Carry on from **Succeeded**, not from the last body step. Defaults are 3 attempts, a 1 second initial delay, 2× backoff, and jitter; the cap is 10 attempts. Only configured error codes retry (defaults include HTTP and node execution failures). Delays between attempts use durable backoff so runs survive restarts.

Retry bodies cannot nest another **Retry** or **For each**. When the body calls Slack, email, AI, or non-idempotent HTTP actions, enable **Acknowledge duplicate risk** in the Retry configuration, or make HTTP calls idempotent (GET, or a custom `Idempotency-Key` header on POST). Publish validation blocks non-idempotent retry bodies without that acknowledgement. Retry outputs include `attemptNumber`, `exhausted`, and optional `lastErrorCode` / `lastErrorMessage`.

Conditions use true/false connections. Switches use case/default connections. Action failures can stop, continue with a visible handled error, or select an error branch. A merge waits for all incoming connections to settle and runs if any is selected.

**Compare** evaluates typed values and outputs a boolean `result` you can wire into **If**, **Wait**, or other steps. Operators include equality and ordering on strings and numbers (`equal`, `not_equal`, `greater_than`, `less_than`, and related), string checks (`contains`, `starts_with`, `ends_with`), and boolean combinators (`and`, `or`, `not`). Wire `value.left` and `value.right` (or a single operand for `not`) on the canvas; values are compared without implicit type coercion. Deep equality works on plain objects and arrays within documented depth and size limits. Locale-aware string checks use an optional locale when you configure one.

## Build and read structured values

Use these steps when an HTTP or webhook payload needs shaping before Slack, email, or **Call workflow** inputs.

| Step | Purpose |
| --- | --- |
| **Set fields** | Assign named outputs from wired values or templates. |
| **Create object** | Build an object from declared fields with optional defaults. |
| **Merge objects** | Combine multiple objects with a conflict policy (`prefer_first`, `prefer_last`, or shallow merge). |
| **Get field** | Read a value at a safe path (property names and array indexes). Outputs `value` and `found`. |
| **Default value** | Return the first non-empty value from an ordered list of wired inputs. |

**Get field** rejects unsafe keys such as `__proto__` and stops at a maximum path depth so arbitrary user data cannot escape the workflow sandbox.

## Parse, serialize, and validate JSON

These steps share the same size and depth limits as webhook bodies (256 KiB of text, depth 32, up to 10,000 object entries). Values must be JSON-compatible (finite numbers, no `undefined`).

| Step | Inputs | Branches | Outputs |
| --- | --- | --- | --- |
| **Parse JSON** | JSON text | **Success** / **Invalid** | Parsed `value`, or `error` with code and path on **Invalid** |
| **Stringify JSON** | Any JSON-compatible value | **Success** / **Error** | `text`, or `error` when the value cannot be serialized |
| **Validate schema** | Value and a JSON Schema object | **Success** / **Invalid** | `valid`, `errors` (up to 50), and the bounded `value` |

**Validate schema** accepts a bounded subset of JSON Schema: `type`, `properties`, `required`, `items`, `enum`, `const`, numeric and length limits, and boolean or nested `additionalProperties`. `$ref` and other open-ended keywords are not supported. Wire **Invalid** into an error branch or a **Fail** step when upstream systems send unexpected shapes.

Typical pattern after a **Webhook** trigger: **Parse JSON** on `body` text → **Validate schema** → **Get field** for nested IDs → **Set fields** or **HTTP Request** for downstream calls.

## End the run on purpose

Use **Stop**, **Return**, and **Fail** when a branch should finish the workflow without running every downstream step.

| Node | When to use it | Run outcome |
| --- | --- | --- |
| **Stop** | The workflow succeeded or should exit without treating the exit as an error | **Completed** marks the run successful. Optional reason text appears in run details. **Cancelled** ends the run as an intentional stop (for example nothing left to process). |
| **Return** | A branch should exit early and expose structured values to callers | Declare up to 32 named outputs, then wire each one (`value.<outputId>`) on the canvas; the **Configuration** tab lists them. Run history stores the returned map by public output name. **Return** inside a **For each** body exits the whole workflow, not just the current item. |
| **Fail** | A branch should stop with a stable, machine-readable error | Set an error code (uppercase letters, digits, underscores; for example `INVALID_ORDER`) and a short message (up to 500 characters). The run fails at that node with a controlled terminal error. |

These nodes have no outgoing execution edges. When one runs on a parallel path, unsettled sibling branches are cancelled so later steps do not keep executing.

## Start from an inbound webhook

Use a **Webhook** trigger when another system should start the workflow with an HTTP POST, for example a CMS event, a TMS callback, or a CI notification.

1. Add **Webhook** as the only trigger, then **Save** the workflow.
2. On the trigger's **Configuration** tab, copy the **Webhook URL**. The URL includes a secret token; anyone with it can start the workflow, so treat it like a password.
3. **Publish** and keep the workflow **Active**. Paused workflows ignore inbound requests.
4. Send `POST` to the URL with the token in the `x-hyperlocalise-webhook-token` header or the `token` query parameter. The request body becomes the trigger's `body` field (JSON object when the payload is JSON; form fields when `Content-Type` is `application/x-www-form-urlencoded`; plain text otherwise). Query parameters are exposed as `query`. Each delivery gets a `deliveryId`.
5. Optional: send an `Idempotency-Key` header so retries start only one run. Without it, Hyperlocalise generates a delivery id per request.
6. To invalidate a leaked URL, select **Reset URL** on the trigger. The old URL keeps working until you **Publish** again.

The endpoint accepts bodies up to 256 KiB and responds with `202` when a run is queued. Duplicate deliveries with the same idempotency key return the original run id. Webhook-triggered workflows are not reusable with **Call workflow** (that contract requires a **Manual** trigger).

## Send reviewed translations to another project

To [translate through another language first](/platform/projects/files#translate-through-another-language-first) without sending each file by hand, send a file to the second project when its review task is done:

1. **Job changed**: choose the first project, for example the one with Chinese source files. Set **Changes** to **Status changed**, **Job kinds** to **Proofread** and **New status** to **Succeeded**. Leave **Changes** on **Status changed**: with other changes, editing a finished task's title or due date would start the workflow again.
2. **Use translation as source**: leave **Job ID** as `{{ trigger.jobId }}` and choose the second project in **Send to project**. Its source language must be the in-between language, such as `en-US`.
3. **Publish** and keep the workflow **Active**.

When a reviewer selects **Mark done** on the task, the run starts within a minute and sends the task's file to the project to send to, as **Use translation as source…** on **Files** does. Create the tasks with an **Assign task** step as **Proofread** tasks, for example in a **Source upload** workflow that machine translates each new file and assigns a **Proofread** task in the in-between language. **Post-edit** is a job kind of its own on this trigger, so marking a post-edit task done does not send the file before it is proofread.

The step sends Word and Excel files on the project's default branch only, and never replaces a file in the project to send to that it did not send.

When a person must act before the file can go, the step fails. With **If this step fails** on **Stop workflow**, the run shows as failed: fix the cause, then retry the run from its history. With **Error branch**, connect the step's error path to **Notify Slack** or **Send email** with `{{ nodes.<step id>.error.message }}`. With **Error branch** or **Continue workflow**, the run counts as handled and cannot be retried, so once the cause is fixed, send the file with **Use translation as source…** on **Files**. To try the error path with **Test workflow**, set this step's test data to fail first.

| Error | What to do |
| --- | --- |
| `translations_not_approved` | The task was marked done while some strings had no approved translation. Approve them, then retry the run or send the file from **Files**. |
| `destination_file_replaced` | The project to send to has a file at this path that this file did not send. Send the file once with **Use translation as source…** on **Files** to replace it. |
| `destination_branch_protected` | The project to send to has a protected default branch. Unprotect it, then retry the run or send the file from **Files**. |
| `source_file_not_ready`, `source_file_read_failed` | A newer upload of the file is still being read, or could not be read. Retry once it is read, or upload it again. |
| `file_reads_differently`, `file_cannot_be_written` | The file cannot be sent as it is; see [Files](/platform/projects/files#translate-through-another-language-first). |

A workflow cannot be published while the step has no **Job ID** or no **Send to project**, or while **Send to project** is the trigger's project. The step also fails when the task or a project no longer exists, or either project's files are kept in a connected TMS. The trigger needs the first project: with **Any project**, a finished task in any other project that translates into the in-between language would be sent too, so the workflow cannot be published that way. To send finished tasks from every such project on purpose, tick **Send tasks from any project** on **Use translation as source**; tasks in other languages then end with `task_in_other_language`. Building or storing the file can also fail; retry the run.

When there is nothing to send, the step succeeds with `sent` set to `false`, and `reason` and `message` say why:

| `reason` | What it means |
| --- | --- |
| `already_sent` | The project to send to already has this file with these translations. |
| `sent_from_destination` | The file's content came from the project to send to, so it is not sent back. |
| `task_has_no_file`, `task_in_other_language` | The task is not about one file, or not in the source language of the project to send to. A project to send to whose source language is none of the task's languages also ends here, so check it if every run says this. |
| `source_file_not_found` | The task's file was removed from the project. |
| `unsupported_file_format`, `no_strings` | Not a Word or Excel file, or a file with no strings. |
| `not_on_default_branch` | The file is on another branch of the project; only the default branch is sent. |

Each finished task sends its file once. A translation changed after the send is not sent again by itself: the file shows **Changed since sent** on **Files**, and **Use translation as source…** sends it again. In the second project, a file the workflow sent reads **Sent here automatically from** the first project.

## Pause for a reviewer

**Human approval** pauses the run until an authorized reviewer decides. Configure a reviewer (a person or a team), optional prompt text, and a deadline. A [vendor](/platform/workspace/roles#vendors) cannot be the reviewer: the step fails with `vendor_cannot_approve`. The reviewer opens the request from **Inbox** and chooses **Approve**, **Reject**, or **Request changes**. If nobody decides before the deadline, the request expires and the error branch can continue. Wire the decision into later steps; do not treat a paused run as failed.

## Route people and due dates

Human steps in MTPE and TEP flows can set owners and deadlines on native jobs and Crowdin tasks.

| Step | Use it to |
| --- | --- |
| **Pick assignee** | Choose one person from a ordered rule table on locale, job type, size, and due date. Spread work **first listed**, **round-robin**, or to the **least busy** person (fewest open native jobs, or open Crowdin tasks when people come from Crowdin). Wire `assigneeId` into **Assign task** or **Update job**. |
| **Assign task** | Create a translate, post-edit, or proofread task on a source file with an optional assignee and **due date** (ISO 8601, for example `2026-05-01T17:00:00Z`). A post-edit or proofread task can go to a [vendor](/platform/workspace/roles#vendors) or to a member outside the project's team, who then work on that task's file only; choose a member whose role can work on jobs, because a read-only member can open the task but not finish it. A translate task cannot go to a vendor. The assignee finishes a post-edit or proofread task with [**Mark done**](/platform/translation/jobs#finish-a-proofread-or-post-edit-task). To make a post-edit or proofread task wait, wire an earlier **Assign task** or **Machine translate** step's `jobId` into **Comes after**: the task opens when that job is marked done, finishes, or is cancelled, so one run can machine translate a file and set up both tasks. To act when a task is finished, start another workflow from **Job changed** with **Job kinds** set to **Post-edit** or **Proofread**. In later steps the trigger's `jobKind` is `proofread` for both; its `taskStep` tells them apart (`edit` for post-edit). |
| **Update job** | Reassign a native job, rename it, or set or clear its due date. Leave assignee or due date empty to keep the current value. |
| **Crowdin task** | Create Crowdin translate or proofread tasks with optional assignees and a deadline. |

On **Pick assignee**, rules are checked from top to bottom; the first rule whose conditions all match wins. An empty condition matches anything. A rule that sets **Due within (hours)** only matches work that already has a due date within that window (or overdue). Multi-locale work must match every locale on the rule. **People from** can be workspace members or Crowdin project members (by Crowdin user id). If no rule matches and fallback people are empty, the step fails so an error branch can handle it.

Job types accept common aliases such as `post-edit`, `MTPE`, and `review` for translate, edit, and proofread steps.

## Call reusable workflows

**Call workflow** runs a **pinned published version** of another visual workflow as a subworkflow. Use it to share a reviewed branch (validation, notifications, enrichment) across many parent workflows without copying nodes.

### Make a workflow reusable

A published workflow appears in the Call workflow picker only when it defines a stable contract:

1. Use a **Manual** trigger only. Scheduled, GitHub, and source-upload triggers are not reusable.
2. On the trigger's **Outputs** tab, declare **output fields** (`path` and type). These paths are the subworkflow **inputs** callers must supply.
3. Add a **Return** node and declare named outputs with types. Every **Return** on the canvas must expose the same output set. These fields are what the Call workflow step exposes to downstream nodes.
4. **Publish** the workflow. Callers pin a specific version number; changing the draft does not affect runs until you publish again.

### Call from a parent workflow

1. Add **Call workflow** and select the reusable workflow and version.
2. Wire each `value.<fieldId>` input on the canvas from upstream data, or use the Configuration tab rows that say to connect on the canvas. Input and output field IDs and types must match the target workflow's published contract at publish time.
3. Use the step's success output paths (`value.<outputId>`) like any other step. Configure **On error** the same way as HTTP or Slack steps.

Publish validation blocks missing workflows, wrong versions, contract mismatches, direct recursion, and call chains deeper than eight levels. Mock a Call workflow step on its **Test** tab like other steps that call out.

## Undo and redo edits

**Undo** and **Redo** in the editor header walk back and forward through your edits in order. You can also press Ctrl+Z and Ctrl+Shift+Z (⌘Z and ⌘⇧Z on a Mac). Hover either button to see which edit it applies to.

Each of these is one step:

- Adding a step, or removing one together with its connections.
- Connecting or disconnecting two steps.
- Moving a step. A drag counts once, when you drop it.
- Changing a step's settings or its type. Typing in one setting is grouped into a single step.
- Renaming the workflow.

When an undo or redo changes the settings of a step whose settings panel is closed, a notice names the change and offers the way back. A step that appears or changes without you selecting it, for example one that an undo brings back, has a violet band until you select it.

Undo and redo change the draft on the canvas only. Nothing is saved or published until you select **Save** or **Publish**. The history is cleared when you reload or leave the page, and the editor does not warn you about unsaved changes, so save before you leave.

## Build with the assistant

Select **Configure with assistant** in the editor header to describe what the workflow should do in your own words. The assistant opens beside the canvas and changes the draft directly: it adds and removes steps, connects them, fills in their settings, and renames the workflow. Each request it carries out is one step that **Undo** takes back, after asking. Steps it adds are marked with a violet band until you select them.

The assistant writes values the way you would on the **Configuration** tab, including fields of earlier steps such as `{{ nodes.notify_slack.sent }}`. It tells you about any reference that cannot be read when the step runs.

It leaves some things to you: picking a Slack channel, credential, connection, project, repository, or the workflow a **Call workflow** step runs; filling each step's **Test** tab; and saving, testing, and publishing. Its conversation for a workflow is yours alone and stays with that workflow.

## Test, save, and publish

Tests use test data unless you choose otherwise. A test follows the same bindings, branches, and loops as a real run. Set the values a test uses on the **Test** tab of the trigger and of each step that calls out: HTTP, AI, Slack, email, content sync, and Call workflow. The trigger's values are its sample event. A step's values are what it returns in place of doing its work. Other steps, such as If, Set fields, Wait, and Merge, work out their own results from their inputs.

Nothing is made up. A test does not start while a value it needs is empty, and it names the first one and opens its **Test** tab. **Fill with examples** writes example values that you can see and change, and **Use last run** copies the step's output from the last test. In the run history, **Use as test data** copies a past run's values into every step. After a test, hover over a pin to see the value that passed through it.

On a step's **Test** tab you can also choose:

- **In a test run: Run for real.** The step calls out for real when you test: requests are sent, content is generated, and messages are delivered. A broadcast mark on the step shows it on the canvas. Its test data is kept for when you switch back to **Use test data**.
- **Outcome: Fails.** The step fails with the error code and message you give instead of returning its test data. What follows depends on its **On error** setting: the test stops, goes on, or takes the step's error path.

Before a test in which any step runs for real, the editor lists those steps and asks you to confirm. It also names any of them that use test data from a mocked step, because such a step acts for real on test values. In **Test settings** beside **Test workflow**, you can see how many steps run for real and set all of them to use test data or to run for real at once. When every step runs for real, the test is a live run, in which Wait steps really wait. A test never publishes your draft.

Test data and these choices are saved with the draft when you select **Save**. They are never published.

**Save** updates the draft. **Publish** validates and activates an immutable version. Active workflows continue using the published version while you edit or test. Concurrent changes return a conflict rather than overwrite another editor's work. Pause prevents new automatic runs; it does not cancel existing runs.

## Credentials

Create or select an organization credential for HTTP authentication. Sensitive header and body fields can reference a credential using a destination such as `headers.X-API-Key` or `body.token`. Do not place credentials in URLs or literal authentication fields. Slack and email use the existing organization connections.

## Inspect and recover runs

Open a historical run to see its executed graph, version, mock/live mode, and node details independently of the current draft. In a test run, the steps that ran for real are marked. Details include redacted inputs and outputs, errors, iterations, and attempts. Skipped, blocked, cancelled, handled-error, and needs-attention states remain visible.

Cancel stops further steps and supported requests. An external action may already have completed. If a run needs attention, inspect the provider before retrying: retry requires acknowledgement that an uncertain action might be duplicated. Successful completed actions are retained during recovery.

## Limits

A workflow supports 200 nodes, 400 connections, 100 loop items, and 1,000 execution steps. HTTP requests time out after 30 seconds, AI requests after 120 seconds, and a run after 15 minutes. HTTP responses must fit the shared security size limit and contain valid JSON when declared as JSON.

Arbitrary code nodes, nested loops, and nested retry regions are not supported.
