title: "Localize HubSpot"
description: "Import HubSpot emails and blog posts, translate them in Jobs, and push unpublished locale copies."
---

Hyperlocalise translates the copy. HubSpot does not. Import reads primary marketing emails and blog posts. **Push to HubSpot** writes unpublished locale copies and leaves the source unchanged. Nothing is published.

Forms, landing pages, and website pages are temporarily unsupported.

## Prerequisites

| Requirement | Description |
| --- | --- |
| Native project | A [native project](/platform/projects/create-project) whose source locale matches the language of the HubSpot source. Add a project target locale for each language you will push back. |
| HubSpot account | Connect HubSpot from **Integrations**. The authorization needs the `content` scope. |
| Locale mapping | HubSpot language codes are lowercase, with a hyphen when they include a region (`fr`, `fr-ca`, `pt-br`, `en-gb`, `zh-cn`). `fr` and `fr-ca` stay different languages. A project tag such as `fr-FR` maps to `fr` when HubSpot has no `fr-fr` code. The locale copy keeps the full tag in its name (`Launch [fr-FR]`). |
| Blog languages | In HubSpot, open **Settings → Blog**. On that blog, choose **Add/edit multi-language variations** and add each language you will push. When that language is on the blog, push creates or updates an unpublished post draft. It does not add a language to the blog. A missing language skips that locale and leaves a warning; the run still succeeds. |

## Connect HubSpot

Open **Integrations** and choose **Connect** on **HubSpot**. Authorize the HubSpot account in the window that opens. The connection uses the existing `hubspot` WorkOS Pipes provider. The token is not stored in Hyperlocalise. The marketplace app source is in `apps/hubspot-app`.

## Translate HubSpot content

Add the **Translate HubSpot content** template from **Popular** or **Marketing**. It is mutually exclusive with Braze, Customer.io, and Loops. Choose the native project, then activate the automation.

On the HubSpot tool, tick the emails and blog posts to translate. Nothing is imported until at least one item is ticked. Locale copies stay out of the tree. Set **Existing HubSpot translations**: **Only empty locales** (default), **Refresh imported locales**, or **Overwrite all locales**. **Overwrite HubSpot copies when the remote copy is newer** is on by default. Uncheck it to keep copies that teammates edited after the last push.

A scheduled or manual run imports content. It does not push. Push runs only when you choose **Push to HubSpot** in the Content editor.

## What import writes

Import reads primary marketing emails and writes `hubspot/emails/{id}/{slug}.html`, with the subject, preview text, and translatable widget fields.

Import reads primary blog posts and writes `hubspot/blog-posts/{id}/post.html`, one HTML document with inlined template CSS for preview and email-style sections for title, meta description, summaries, body and RSS copy (when RSS text differs from the article body), and widget or layout text.

When a blog post has no saved module edits, import reads that template and included sections. The default copy the editor shows is imported from there. A blog post that already has an article body still picks up section text from its layout or template. Push writes the translation onto the locale draft and leaves the template unchanged.

Import skips posts that are already language variations, and names that already look like locale copies (`Launch [fr-FR]`). Field names, widget ids, URLs, and colors stay locked. Import does not write anything to HubSpot.

A later import still checks mapped target locales when the source has not changed. If HubSpot already has a locale copy or language variation, import can seed that copy as an approved translation. **Only empty locales** never overwrites work already in Hyperlocalise.

When **Create native TMS job** is enabled, the run opens a job for mapped locales that still need translation. Locales just seeded from HubSpot are left out.

A project locale maps to a HubSpot code in this order:

1. The same code, lowercased, with `_` written as `-` (`pt-BR` becomes `pt-br`).
2. A short list of aliases HubSpot uses: `zh-CN` becomes `zh-cn`, `zh-TW` becomes `zh-tw`, `he` becomes `he-il`, and Norwegian tags become `no-no`.
3. The language alone, when HubSpot accepts that language and has no matching regional code (`fr-FR` becomes `fr`).

When two project locales become the same HubSpot code, the second locale is skipped. The source object's language must match the project source locale. An empty object language is treated as a match.

## What push writes

1. Translate and [approve](/platform/cat) the mapped locales you want to write back.
2. In the Content editor, choose **Push to HubSpot** and select the mapped emails and blog posts.

An email push clones the source, then writes a draft with the target language and the translated subject, preview, and widgets. The source email stays as it was.

Add the languages on the blog first. In HubSpot, open **Settings → Blog** and choose **Add/edit multi-language variations**. When that language is on the blog, push creates an unpublished post draft or updates the existing variation. It does not add a language to the blog. If the language is missing, that locale is skipped with a warning and the run still succeeds.

The HubSpot post title is the translated post name, or the translated HTML title when the name has no translation yet. The draft gets the translated title, meta description, summary, body, section text, and static module fields. The post stays unpublished.

HubSpot's own translate actions are not used. Hyperlocalise writes the approved strings onto the copy.

A later push skips a locale whose approved content already matches the last successful push. **Only empty locales** pushes only to copies that carry no locale content yet, so it never overwrites a copy that already holds translations. **Refresh imported locales** pushes a locale again only when its approved content changed since the last push.

## Change or remove access

Disconnect HubSpot from **Integrations** to stop this workspace using that account. Inspect automations that depend on the connection before you disconnect.

## If import or push does not run

- Confirm HubSpot is connected and the automation is **Active**.
- Confirm the HubSpot authorization still has `content`.
- Open **Settings → Blog** in HubSpot and choose **Add/edit multi-language variations**. When that language is on the blog, push creates or updates an unpublished post draft. It does not add a language to the blog. A missing language skips that locale and leaves a warning; the run still succeeds.
- Confirm the project source locale matches the language of the HubSpot source.
- Confirm each target locale maps to a HubSpot language the account has enabled.
- Open **Run History** for the failed item or locale.

See [Automation troubleshooting](/platform/help/automations) and [Connection troubleshooting](/platform/help/connections).

## Known limitations

| Content | Status |
| --- | --- |
| Emails | Supported (`hubspot/emails/{id}/{slug}.html`) |
| Blog posts | Supported (`hubspot/blog-posts/{id}/post.html`) |
| Forms | Temporarily unsupported |
| Landing pages | Temporarily unsupported |
| Website pages | Temporarily unsupported |

Import skips unsupported content, and it does not appear in **Content to translate**.
