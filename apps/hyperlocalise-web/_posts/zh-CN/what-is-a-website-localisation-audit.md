翻译网站只是本地化工作的起点。

网站即使有翻译后的页面，也仍可能让国际用户体验不佳。缺少 `hreflang` 标签会影响内容的可发现性。未翻译的行动号召可能让访客感到困惑。技术上正确的翻译仍可能使用错误的产品术语。较长的德语字符串可能会导致移动设备上的按钮显示异常。

本地化审计要回答的问题不是“翻译了多少条字符串？”，而是：

> **你的网站是否让人觉得它确实是为当地用户打造的？**

Hyperlocalise 本地化审计会从技术、语言、语境和视觉四个维度检查网站，并给出满分 100 分的本地化评分，以及需要优先修复的问题。

## 本地化审计涵盖的内容

本地化审核不是翻译检查器，也不是通用的网站审核。

性能、无障碍访问和 SEO 工具关注的是实现方式。翻译质量检查关注的是准确性、语法和流畅度。两者都无法全面反映多语言网站的情况。

本地化审计结合了这两个视角：

| 审计             | 权重   | 它回答的问题                                            |
| ---------------- | -----: | ----------------------------------------------------- |
| 技术审计  |    25% | 本地化是否正确实施？                |
| 语言审校 |    25% | 翻译是否准确、自然且一致？   |
| 上下文审查 |    25% | 本地化是否符合您的产品语境？ |
| 视觉审核     |    25% | 本地化后的用户界面外观和行为是否正确？      |

您将获得总体评分、各个领域的评分，以及包含严重程度、证据和置信度的可操作发现。

## 如何解读分数

总体评分是健康状况指标，不能替代详细的检查结果。请始终优先查看严重程度最高的问题。

| 得分  | 评级              | 含义                                                                  |
| ------ | ----------------- | -------------------------------------------------------------------- |
| 90–100 | 优秀                | 本地化体验状况良好                                                   |
| 75–89  | 良好              | 网站的本地化总体不错，但仍有一些问题需要改进 |
| 50–74  | 需要改进 | 用户可能会遇到明显的本地化问题                 |
| 25–49  | 较差              | 显著的本地化差距正在影响使用体验           |
| 0–24   | 严重          | 本地化体验存在重大问题，应予以解决 |

一个网站的总体评分可能不错，但结账流程、路由或高流量页面仍可能存在关键问题。评分会告诉你该从哪里查起，而发现的问题会告诉你该修复什么。

## 技术审计：本地化是否已正确实现？

技术审计会检查多语言网站背后的基础设施：可发现性、路由、格式、无障碍性，以及用户和搜索引擎能否访问正确的语言区域。

### 语言环境检测与路由

页面应正确声明其语言和区域设置，例如 `<html lang="fr-FR">`。审核会检查语言声明缺失、语言或地区代码错误、区域设置与内容不匹配，以及标识符不一致。

它还会检查本地化页面是否使用一致的 URL 结构：

```text
/en/pricing
/fr/pricing
/de/pricing
```

常见问题包括缺少本地化路由、区域设置 URL 损坏、重定向不正确、意外回退到默认区域设置，以及区域设置持久化问题。

### 语言切换器和 `hreflang`

访问者应能够更改语言区域，同时不会丢失当前查看的页面。从 `/fr/pricing` 切换后应跳转到 `/de/pricing`，而不是德语主页。

审核还会检查页面各本地化版本之间的关系：缺失的 `hreflang`、错误的语言或地区代码、无效的 URL、缺少相互引用或自引用、错误的 `x-default`，以及与规范 URL 的冲突。

本地化页面通常应将规范网址指向自身。法语定价页面将规范网址指向英文版本，是一种常见的 SEO 错误：

```text
/fr/pricing
canonical → /en/pricing
```

### 元数据、站点地图和结构化数据

重要的页面元数据应进行本地化：标题、元描述、Open Graph 标题和描述、`og:locale`以及社交分享元数据。

审核还会检查本地化网址是否出现在站点地图中并能正确解析；在适用情况下，还会检查 Product、WebPage、Breadcrumbs、FAQ、Organization、Article 和 LocalBusiness 等结构化数据是否已本地化。

### 国际化格式和无障碍访问

区域设置敏感的值应与区域设置相符：

```text
US:  $1,234.56
DE:  1.234,56 €
FR:  1 234,56 €
```

这包括日期、时间、数字、货币、计量单位和时区。

无障碍本地化涵盖 `lang`、`aria-label`、无障碍名称、表单标签、验证消息和图像 `alt`文本。

## 语言审核：语言是否准确、自然且一致？

语言审查会评估页面上的语言。它不只是检查文本是否已翻译，还会判断译文是否准确传达原意，读起来是否符合目标地区用户的语言习惯。

### 完整性和准确性

未翻译的内容会被标记，而品牌名称、产品名称、URL、电子邮件地址、代码、专有名词和有意保留的英文术语则视为预期例外。

一个法语页面，上面写着：

```text
Bienvenue sur notre site.

Start your free trial
```

会因行动号召未翻译而被标记。

准确性检查会查找缺失或新增的含义、错误的解读、错误的数字、错误的产品操作以及不正确的术语。

### 流畅度、术语和品牌调性

翻译在技术上可能正确，但听起来仍不自然。审核会检查措辞生硬、句式不自然、语法和拼写问题、机器翻译痕迹，以及是否符合当地的写作习惯。

它还会识别网站中翻译不一致的概念：

```text
Workspace

Page 1 → Espace de travail
Page 2 → Workspace
Page 3 → Espace Workspace
```

如果项目有经批准的术语表，应优先使用术语表中的术语。

品牌语言风格会根据预期语气进行评估——专业、友好、简洁、技术性、对话式、高端或活泼，同时也会考量符合当地习惯的语法和风格，例如大小写、标点、正式程度和一致性。

## 结合上下文审核：此产品的翻译是否正确？

语境是本地化中最容易被忽视的部分之一。

翻译在语法上可能完全正确，但放在具体场景中仍然不合适。“Cancel”可能指关闭对话框、取消订阅、取消订单或停止操作。正确的译法取决于产品语境。

上下文审核会结合页面、用户界面、术语和产品上下文，评估译文在实际使用场景中是否合理。

### UI、产品和行动号召意图

审核会考虑字符串出现的位置——按钮、导航、表单、模态框、工具提示、标题、错误消息、通知、菜单或结账页面——并根据页面上的产品概念评估语言：功能名称、套餐、设置、账户概念、工作流操作和产品术语。

行动号召尤其值得关注。“开始免费试用”、“立即预订”、“保存更改”、“删除账户”和“升级”必须在目标语言环境中准确传达预期操作，而不能使用泛泛的译法。

### 术语表、翻译记忆库和文化

如果有词汇表或已批准的术语，可以据此检查翻译是否符合首选和禁用术语、产品名称及品牌术语。

如果存在先前获批的译文，审核可以识别出与翻译记忆的偏差。

文化适配会检查货币、日期、度量单位、地址、电话号码、支付习惯、本地示例、文化典故和习语。并非所有差异都是错误。对于文化适配方面的发现，会酌情作为建议或待审查的问题呈现。

受众背景也很重要。适合面向消费者的旅行产品的语言，可能不适合企业级开发工具、金融产品或医疗健康领域。

## 视觉审计：本地化后的网站是否真的能正常运行？

语言会改变内容的大小、形状和布局。视觉审计会评估渲染后的页面，以发现仅凭源字符串无法检测到的问题。

### 溢出、布局和文本扩展

英文“Start free trial”在德语中译为“Kostenlose Testversion starten”。如果德语版本不再适合按钮，审核就会将其标记出来。

其他视觉问题包括文本被裁切或截断、出现意外的省略号、导航和表格溢出、元素重叠、网格错乱、内容未对齐、模态框溢出、意外换行以及间距不正确。

本地化页面在移动端、平板和桌面端宽度下也可能表现不同。审核可以评估这些断点下的关键布局。

### RTL、字体和本地化资源

对于阿拉伯语和希伯来语等从右到左书写的语言，审核会检查文本方向、布局镜像、导航、对齐方式、图标、表单、侧边栏和模态框。

字体排版必须支持目标文字体系，包括阿拉伯语、中文、日语、韩语、泰语、越南语和西里尔字母。缺失字形、意外的备用字体、不一致的字体排版、不正确的行高以及渲染问题都会被标记出来。

语言专属的视觉素材同样重要。即使页面上的所有字符串都已翻译，如果法语页面中包含英文界面的截图，也仍然存在本地化缺漏。

审核还会检查本地化是否改变了视觉层级：标题是否过长、行动号召按钮是否换行、重要文本是否失去强调效果、卡片高度是否不一致，以及导航是否变得难以快速浏览。

## 如何确定发现的优先级

并非所有问题的影响都相同。每项发现都会被赋予一个严重性级别，以便团队优先修复重要问题。

**严重**问题可能会严重损害本地化体验：语言区域不可用、页面完全未翻译、提供了错误的语言区域、结账货币不正确、RTL 布局出现重大错乱，或本地化路由无法访问。

**高**级别问题会影响可用性、SEO 或翻译质量：缺少 `hreflang`、主要行动号召未翻译、重大翻译错误、导航失效、重要文本被截断或产品术语错误。

**中等**问题较为明显，应予以处理：术语不一致、缺少本地化元数据、次要内容未翻译、轻微视觉溢出或缺少本地化替代文本。

**低**级问题属于质量改进项：措辞略显不自然、风格略有不一致、小的格式问题，或可选的元数据改进。

**信息**项是建议或机会，不一定是错误。

AI 驱动的发现还会在适当情况下标注置信度。高置信度的发现更可能是客观或确定性的，例如缺少 `hreflang`。低置信度的发现（例如潜在的文化适配问题）应视为待审核的建议，而非确定的错误。

## 审计如何运作

审计从网站 URL 开始，发现可用的语言区域，抓取本地化页面，提取内容和元数据，渲染页面，然后运行四个分析引擎，最后计算评分并生成报告。

区域设置发现会使用多种信号，例如 URL 结构、`hreflang`、站点地图、语言选择器、HTML 元数据以及域名或子域名。

实际页面的呈现效果很重要。翻译后的内容常常会导致 HTML 源代码中并不存在的视觉问题。报告包含总体本地化评分、四个模块的评分、按严重程度分组的问题、受影响的页面、证据、置信度和建议采取的操作。

## 从发现到持续质量

审计不应止步于告诉你哪里出了问题。

当 Hyperlocalise 发现问题时，该发现可以成为修复问题的起点：未翻译的内容可以进行翻译，术语不一致之处可以对照已批准的术语进行审核，违反词汇表规范的内容可以更新，缺失的元数据可以进行本地化，视觉溢出问题可以通过调整文案或布局来解决。

这就形成了一个持续的工作流程：审计、发现问题、修复、再次审计、监控并检测回归。

本地化并非一次性项目。每个新功能、页面、版本或翻译都可能引入新问题——新的英文字符串、缺失的翻译、术语表违规、损坏的 `hreflang`、不正确的元数据、视觉溢出或路由回归。

对于持续发布的团队，目标是从一次性本地化审计转向持续的本地化质量监控。

这正是我们在[什么是翻译智能？](/blog/what-is-translation-intelligence)中描述的转变：翻译产出已不再是瓶颈，判断力、上下文和回归检测才是。

## 常见问题

### 这是一个翻译检查器吗？

不完全是。翻译检查工具主要关注语言质量。Hyperlocalise 本地化审计会评估整个本地化网站，包括技术实现、SEO、产品语境和视觉界面。

### 翻译后的网站会自动获得高分吗？

不。网站即使内容已完全翻译，在`hreflang`、区域设置路由、货币、日期格式、术语、产品语境、视觉布局和无障碍访问方面仍可能存在问题。评分评估的是整体体验。

### 审核能检测出未翻译的内容吗？

是的。它会分析本地化页面，识别其中似乎仍保留源语言的内容，同时考虑品牌名称、网址、产品名称以及其他可能有意保持不变的内容。

### 它能检测出糟糕的翻译吗？

审核可以识别涉及含义、流畅度、术语、语法和一致性的潜在问题。AI 提供的发现会附带置信度信息，帮助团队区分可靠的发现与可能需要人工审核的项目。

### 它能检测视觉问题吗？

是的。视觉审计会评估渲染后的本地化页面，并可识别文本溢出、布局错乱、响应式问题、RTL 问题以及本地化资源问题。

### 低评分是否意味着网站无法使用？

不一定。评分是健康状况指标。请务必查看各项发现及其严重程度。网站的总体评分可能不错，但仍可能存在一个影响重要页面或用户流程的严重问题。

## 在用户发现本地化问题之前，先找出它们。

传统的网站审计衡量性能、无障碍性和 SEO。翻译质量保证衡量准确性、语法和流畅度。本地化审计会同时提出四个问题：

- 本地化是否已正确实现？
- 翻译是否正确、自然？
- 这是否适合该产品、受众和情境？
- 本地化后的体验对用户来说真的好用吗？

综合来看，这些答案能更全面地展现本地化的健康状况。
