构建一个令人印象深刻的 AI 翻译演示，从未如此简单。

将大型语言模型连接到代码仓库，为其提供术语表，并要求它翻译一组字符串。几天之内，产品团队就可以拥有一个看起来像本地化代理的工具。它可能会生成流畅的译文、响应指令，甚至自动创建拉取请求。

这种早期的进展可能会让下一个决策显得显而易见：既然工程团队可以在内部构建代理，为什么还要为本地化平台付费？

答案取决于你实际上想要构建的内容。

生成翻译文本的原型相对简单。要打造一个可靠的本地化代理，使其能够理解产品上下文、遵循特定市场的指导原则、保护变量、在现有系统中运行，并通过人工反馈不断改进，则是一项规模大得多的工作。

重要的问题不是你的团队_能否_构建一个本地化代理，而是拥有并运营这样一个系统所创造的战略价值，是否足以证明持续投入是合理的。

## 本地化代理不仅仅是 AI 翻译器

AI 翻译器接收文本，并以另一种语言返回文本。本地化代理在工作流程中运行。

OpenAI 将代理描述为将模型与指令、工具和防护机制相结合的系统，使其能够代表用户完成任务。Anthropic 同样建议从简单、可组合的工作流开始，而不是增加不必要的代理复杂性。

应用于本地化，这意味着一个高效的智能体需要做的远不止是调用翻译模型。它需要：

- 检索相关的产品、品牌和市场背景；
- 请提供要翻译的文本。
- 保留占位符、格式、标记和技术约束；
- 区分需要翻译、再创作或无需更改的内容；
- 协调审查、审批和修订；
- 与代码仓库、内容系统和翻译平台同步工作；
- 解释其作出决定的原因；
- 将不确定事项上报给合适的人员；并
- 从审阅者的反馈中吸取经验，避免重蹈覆辙。

这一点很重要，因为团队可能会构建翻译步骤，并认为自己已经构建了完整的系统。实际上，翻译生成可能是较为简单的组件之一。

更困难的问题是围绕它构建一个可靠的运营层。

## 为什么构建自己的智能体很有吸引力

有充分的理由考虑使用内部本地化代理。

最明显的优势是控制权。您的团队可以完全决定使用哪些模型、如何构建提示词、在哪里处理数据，以及代理如何与内部系统交互。您不受另一家公司产品路线图或其对本地化应如何运作的假设所限制。

当你的工作流程确实与众不同时，内部构建也可能是合理的选择。一家拥有叙事分支的游戏公司、受监管的医疗平台，或采用专有内容架构的企业，其需求可能无法由通用工具妥善支持。

还有一个战略层面的论点。当本地化技术是产品的核心，而非一项运营职能时，其底层智能可能会成为有价值的知识产权。语言学习公司、多语言搜索服务提供商或人工智能通信产品公司，可能会合理地认为，本地化能力应当纳入其核心平台。

达到足够的规模后，内部系统还可以降低某些供应商成本。然而，这种比较通常只考虑模型 API 费用。真正的成本还包括为确保系统可靠运行而需要投入的工程、基础设施和运营工作。

控制很有价值，但控制也意味着所有权。

## 构建本地化代理的隐性范围

第一个内部版本可能只需要一个模型、一条提示词以及对源字符串的访问权限。投入生产使用后，则会带来更多得多的责任。

### 1. 构建上下文层

翻译质量在很大程度上取决于上下文。代理可能需要了解消息显示的位置、触发该消息的用户操作、周围界面元素的文本，以及内容属于入门引导、计费、支持还是营销。

这些信息通常分散在设计文件、代码仓库、产品文档、屏幕截图、分析数据、工单和对话中。因此，构建代理所需的不只是提示工程，还需要一个上下文检索系统，能够为每项翻译任务识别正确的信息，同时避免让无关数据淹没模型。

上下文也必须保持最新。来自早期界面的截图、过时的术语表条目或已废弃的产品描述，都可能导致看似自信却不正确的翻译。

这就变成了一个数据架构问题：应该索引哪些信息、由谁负责维护、如何更新，以及当信息源相互冲突时，智能体应该信任哪些信息源？

### 2. 支持特定于本地化的格式

产品内容并不总是纯文本。

本地化系统必须处理占位符、复数形式、变量、标签、字符限制和结构化文件格式，同时不能破坏这些内容。例如，XLIFF 用于在本地化工作流程的不同阶段和工具之间传递可本地化内容。Unicode 的 MessageFormat 规范用于处理涉及变量、复数规则、语法匹配、日期和数字的动态消息。

即使译文听起来非常自然，也可能因为模型错误地移动了占位符、翻译了变量、删除了标记，或误解了复数分支的工作方式，从而导致产品出现问题。

因此，您的代理需要将确定性验证与生成式智能相结合。仅有流畅性是不够的。

### 3. 创建一个有意义的评估体系

本地化质量无法通过单一的合格或不合格测试来衡量。

生产环境评估框架可能需要评估含义保留、术语、语气、语法、文化适宜性、格式完整性、长度限制以及与相关内容的一致性。不同的内容类型也需要遵循不同的标准。法律声明不应与营销活动标题或对话式界面消息采用相同的评估方式。

自动化评估可以检测出许多问题，但必须根据人工判断进行校准。您的团队需要具有代表性的测试集、预期结果、懂相关语言的审核人员，以及一种衡量提示词、模型或上下文检索的更改是否改善系统的方法。

没有这一层，模型升级可能会在悄无声息中提升某种语言的质量，却降低另一种语言的质量。

### 4. 集成整个工作流程

当代理能够在本地化工作已经开展的系统中执行操作时，它才会变得有用。

这可能包括 GitHub、设计工具、内容管理系统、客户支持平台、产品数据库、翻译管理系统和内部审批工作流。每个集成都需要身份验证、权限处理、重试逻辑、错误恢复、监控和维护。

工作流程还必须考虑部分失败的情况。如果代理成功翻译了 900 个字符串，却无法处理剩余的 100 个，会发生什么？如果内容在审核期间发生变化，会发生什么？审核人员能否看到哪些上下文影响了翻译结果？已批准的翻译能否追溯到特定的模型、指令集和源版本？

这些是产品和基础设施方面的问题，而不仅仅是 AI 方面的问题。

### 5. 保护敏感数据和系统

本地化代理可能会接触到尚未发布的产品功能、客户沟通内容、内部文档和专有术语。如果它能够执行操作，还可能获准修改内容或将更改推送到生产工作流中。

OWASP 将提示注入和不安全的输出处理列为基于大型语言模型构建的应用程序面临的主要风险之一。检索内容中恶意或意外的指令可能会影响代理，而未经验证的输出则可能在后续环节造成安全问题。

生产系统需要严格的权限边界、输入和输出验证、审计日志、数据保留控制，以及明确规定哪些操作可以自动化的规则。高风险变更可能需要获得明确的人工批准。

NIST 的 AI 风险管理框架还强调，值得信赖的 AI 需要持续的治理、测量和风险管理，而不是一次性的技术审查。

### 6. 发布后维护代理者

模型会变化。价格会变化。API 会变化。产品术语会演变。新市场会带来新的语言需求。集成会中断，安全预期会提高，用户也会发现开发期间未曾察觉的边缘情况。

因此，该代理需要一位持续负责的所有者。

那位负责人并不只是维护代码。他们还在管理模型、工作流、组织知识与人工审核员之间的关系。他们必须调查故障、改进评估、更新指令，并决定何时新功能已经足够安全，可以发布。

本地化代理并不是在第一个版本发布时就结束的项目。它会成为一个内部产品。

## 真正的自建与采购成本核算

内部构建代理的成本并不只是：

> 模型使用量 + 几周的工程开发

一个更现实的计算是：

> 初始开发 + 集成 + 上下文基础设施 + 评估系统 + 安全性 + 可观测性 + 持续维护 + 本地化专业知识 + 机会成本

机会成本尤其重要。

每一位从事本地化基础设施工作的工程师，都没有在开发公司的核心产品。当本地化系统能够创造持久的竞争优势时，这项投入或许值得。但如果目标仅仅是帮助本地化团队更快地发布内容，就更难证明其合理性。

因此，构建还是购买的决策应基于战略差异化，而不是原型看起来是否成本低廉。

## 在构建自己的本地化代理有意义时

当以下大多数条件都满足时，内部构建可能是正确的决定：

- 本地化智能是贵公司核心产品或竞争优势的基础。
- 您的工作流程足够专业化，以至于现有平台无法通过配置或集成来支持它们。
- 您拥有一支专门负责该系统的长期工程团队。
- 您可以获得本地化专家的支持，他们能够设计评估并为产品决策提供指导。
- 外部提供商无法满足您的安全性、部署或数据要求。
- 您的内容规模和运营规模足以证明其总拥有成本的合理性。
- 您的组织已准备好持续维护集成、评估和治理。

在这种情况下，应将该系统视为一个战略平台，而不是内部实验。

团队应在扩大自动化规模之前，明确责任归属、可靠性目标、审批边界和评估标准。同时，在验证更简单的工作流之前，应避免构建复杂的多智能体架构。

## 使用本地化代理平台时更有意义

当本地化支持业务但本身并非业务时，平台通常是更有力的选择。

当主要目标是在不组建新的内部基础设施团队的情况下提高翻译质量、缩短发布周期或减少运营工作量时，尤其如此。

专业化平台可以提供上下文层、工作流编排、集成、质量控制和审校体验，而这些功能原本都需要内部开发。这样，您的本地化团队就可以专注于市场决策和质量，而无需维护 AI 基础设施。

这并不意味着要放弃控制权。合适的平台应让您继续掌握术语、风格、审校政策、翻译记忆库和审批决策的所有权。它还应让您清楚了解代理正在做什么、使用了哪些信息，以及哪些地方需要人工判断。

It should work with your existing localisation stack rather than forcing an immediate migration. As we explored in [How to Add AI Translation Without Replacing Your TMS](/blog/how-to-add-ai-translation-without-replacing-tms), an agent can add intelligence across an existing workflow without requiring the organisation to discard the systems and processes it already relies on.

## 混合方法通常是最强的

这个决定不必完全非黑即白。

许多公司应当掌握自己的本地化知识，同时使用专业平台将其付诸实施。

您的组织可以拥有：

- 品牌与市场策略；
- 术语和风格指南；
- 产品和客户背景；
- 审批政策；
- 质量预期；
- 人工审核员关系；以及
- 关于发布内容的最终决定。

平台可以提供：

- 模型编排；
- 上下文检索；
- 集成；
- 工作流自动化；
- 评估基础设施；
- 可观测性；
- 权限和可审计性；以及
- 随着模型和本地化实践不断演变而持续调整。

这使公司能够保留创造差异化优势的知识，而无需重新构建使这些知识可用所需的技术基础设施。

换句话说，掌握你的本地化智能。谨慎决定是否也需要掌控其周边基础设施。

## 一个实用的决策框架

在批准内部构建版本之前，请询问以下问题：

| 问题                                                | 更强的信号表明应自行构建                                      | 更强的信号表明应使用平台                                    |
| ---------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------- |
| 本地化技术是否属于核心产品的一部分？ | 是，它直接构成产品差异化优势 | 否，它支持产品扩展 |
| 这些工作流程确实独特吗？                  | 现有系统无法支持它们                          | 可通过配置或集成处理       |
| 上线后谁将负责该系统？                | 专门的平台团队                                     | 临时项目团队或单个工程师                |
| 您能评估每个目标市场的质量吗？ | 您拥有语言专家和评估基础设施       | 您主要需要经过验证的工作流程和人工审核           |
| 企业必须多快看到价值？             | 公司可以进行长期投资                  | 团队需要尽快实现运营改进                    |
| 您是否准备好维护每个集成？      | 集成所有权具有战略价值               | 维护工作会分散核心产品开发的注意力              |
| 内部所有权是否创造了持久优势？ | 是的，竞争对手难以复制这一能力 | 不，主要价值来自有效利用这一能力 |

最后一个问题最重要。

定制技术并不一定就是战略性技术。有时，公司会在内部构建某些东西，并以为拥有它本身就能带来优势。但实际上，优势通常来自专有知识、分销能力、客户洞察或独特的运营模式，而不是维护另一层集成。

## 不要仅仅因为你能，就构建一个智能体

语言模型的快速进步降低了试验的门槛，这对本地化行业来说是件好事。更多团队可以测试想法、自动化重复性工作，并探索更好的方式将产品上下文融入翻译。

但降低开发门槛也可能掩盖原型与可靠系统之间的差距。

一个令人信服的演示只能证明模型能够生成译文。它并不能证明系统能够管理上下文、维护产品完整性、支持人工审校人员、确保安全运行，并在数千次变更和多个市场中持续改进。

构建自己的本地化代理，只有在拥有这项能力的重要战略意义足以证明承担所有这些职责是合理的情况下才有意义。

对于大多数产品和本地化团队而言，更好的选择是采用一个能够与现有工具协同工作、以人类专业知识为核心，并让他们掌控那些使其产品独具特色的知识的智能体平台。

这就是 Hyperlocalise 背后的理念。我们正在为本地化团队打造一支 AI 劳动力：由能够收集上下文、运用市场知识、协助翻译和质量保证的智能体组成，帮助团队跟上产品开发的步伐，同时不会取代他们一直信赖的工具或人员。

本地化的未来，不会由谁能将文本发送给语言模型来定义，而会由谁能将组织知识和本地专业经验转化为可靠、可扩展的工作方式来定义。
